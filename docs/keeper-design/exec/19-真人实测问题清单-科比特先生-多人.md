### #34（已修复）房主整局收不到开场旁白，同房玩家正常收到

- **症状**（用户截图两张）：房主「凌铭辉」停在「守秘人正在开场…」+ 打字气泡，
  玩家「张家豪」正常显示了完整开场旁白。两人同一房间、同一时刻。
- **诊断**（后端无辜，有日志支撑）：
  - 后端两条 WS 全程在线（日志无 `connection closed`），
    `keeper_opening_narrated` 正常产出，开场走的是 `manager.broadcast` 全房间。
  - 丢在前端。`RoomPage` 有两个副作用把**对局中途会变化的值**放进了依赖数组：
    - **replay 兜底**（依赖 `senderName`）：依赖一变，进行中的轮询被 `cancelled`
      丢弃；而 `seenEventKeysRef` 此时**已经把这条 eventId 记下了**，重跑时被
      去重跳过 → 这条旁白**永久丢失**。
    - **WS 订阅**（依赖 `senderName`、`roomInfo`）：依赖一变就退订重订阅，
      窗口期内到达的消息直接丢。
  - 两个诱因叠加：① 上一个提交把局内角色卡改成从后端**异步**拉，`senderName`
    因此在进房后必然变化一次（**这是本轮改动引入的**）；② `roomInfo` 来自
    `useRoomPlayers` **轮询**，每次返回都是新对象，等于每隔几秒重订阅一次 WS
    ——这是**既有缺陷**，只是①让它稳定复现了出来。房主先进房、轮询次数多所以
    撞上，玩家后进没撞上，与现象一致。
- **修法**：`senderName`/`roomInfo`/`reloadCharacter` 都只在回调内部用于渲染，
  一律改走 ref；两个 effect 的依赖收敛成整局不变的身份字段。
- **判据（长期）**：**只用于渲染的值不进副作用依赖**；订阅类 effect 的依赖只能
  是"整局不变"的东西，否则**重订阅窗口就是丢消息窗口**。
- **状态**：已修复（`541bfc8`）。⚠️ **没有自动化测试守着**——丢消息发生在 React
  effect 的重订阅窗口，vitest 无真实时序、e2e 无浏览器，现有装置都够不着，
  只能靠真机复测。

### #35（已缓解）AI 主持人回复太慢：多人局单轮约 16 秒

- **症状**（用户原话）："一眼就能确认的，ai 主持人的回复非常慢"。
- **诊断**（events 表时间戳实测）：

  | 局 | `action.submit` → `narration.push` |
  |---|---|
  | 本次双人局（07:28:51 → 07:29:05） | **13.9s** |
  | 对照：改动前单人局（03:28 三轮） | 9.8s / 9.1s / 8.3s |

  拆开：**裁决 10.7s + 叙事 3.2s**。
  ⚠️ 而 `action.submit` 是**收集窗口关闭之后**才落库的，所以玩家实际感知是
  **2.5s（窗口）+ 13.9s ≈ 16 秒**。

  三块成因：
  1. **收集窗口 2.5s**——P5.1 引入，仅多人局（单人局为 0）。
  2. **裁决 10.7s**——system prompt 每轮塞进 `render_full(module)`（模组全文）
     + 92 项技能权威表，user 里是全量历史。**这是既有设计，不是 P5 引入的。**
  3. 叙事 3.2s——正常。
- **🔴 我最初的假设被实测推翻了，记下来防止以后再犯**：我原本判断"每轮塞模组
  全文所以慢"，打算按当前节点裁剪 prompt。**实测证明输入端根本不是瓶颈**——
  对真实 API 打两组对照（scratchpad 脚本，未入库）：

  | 变体 | 耗时 | prompt tokens | 其中命中缓存 | completion tokens |
  |---|---|---|---|---|
  | 现状 | 6.7–7.5s | 11134 | **10880–11008（98%）** | 360–381 |
  | system prompt 砍一半 | 4.9–5.6s | 5817 | 0 / 5760 | 171–322 |
  | 限制 `thinking` ≤30字 | 4.9–6.3s | 11137 | 8448–11136 | **236–264** |

  provider 的 **prompt cache 已经把模组全文覆盖掉了**（98% 命中），输入几乎免费；
  耗时几乎全在**输出解码**（~370 token ≈ 7s，约 53 tok/s）。砍一半 prompt 省下的
  那 2 秒，大部分其实来自它顺带写短了的 completion。

  **各块字符占比**（实测五个模组）：nodes 占 47–85%，是全文的大头——所以"裁剪
  节点"这个想法本身没错，只是**省不到时间**。以后再遇到"prompt 太长所以慢"的
  直觉，先看 `usage.prompt_cache_hit_tokens`。
- **已做的两件（都针对输出端与白等，不动模组渲染）**：
  1. **`thinking` 压到 30 字**——它是纯审计字段、玩家永远看不到，模型却常写成
     200 字小作文，占掉输出的三分之一。实测 completion 370→250、单次 7.0→5.6s。
  2. **收集窗口「人到齐就提前收」**（`_await_window`）——固定 sleep 满 2.5s 是纯
     白等：两人局里两人都提交了，再等下去不会多收到任何东西。改成轮询，凑齐在场
     人数立刻开跑。**不牺牲"多人合并成一拍"**，只砍掉到齐之后那段。单人局窗口为
     0、一次都不轮询，行为逐字不变。
- **诚实结论**：这两下加起来大约 12.5s → 10s 量级，**是 20% 不是 2x**。真正能
  改变体感的是**流式输出**（叙事逐字吐给客户端），那是协议层改造，本轮不做。
- **状态**：已缓解，未根治。流式输出另开。

### #36（已修复）被 `ACTION_IN_PROGRESS` 拒掉的提交，原话却已经广播出去了

- **症状**（用户原话）："明明凌铭辉的消息被这样提示了『守秘人正在处理其他玩家的
  行动，请稍候再试』，但是还是有发出来，这是合理的吗"。
- **诊断**：`ws._handle_action_submit` 的顺序是

  ```
  ① 广播原话                    ← 已经播出去了
  ② 并入收集窗口
  ③ 拿房间锁 → 失败 → drain 窗口 + 回 ACTION_IN_PROGRESS + return
  ```

  被拒时原话**已经广播**，但 `record_event` 从未执行。后果比"没回应"更糟：
  - 两个玩家屏幕上都有这句话；
  - `events` 表里没有 → **守秘人的历史里也没有** → 下一轮裁决器完全不知道
    有人说过这句；
  - 即这句话**在世界里从未发生**，但桌面上大家都以为发生了。

  已核对 events 表：凌铭辉在 07:30 前后确实没有落库记录，与现象吻合。

  **并且这暴露了 P5.1 的立意没兑现**：收集窗口本意是"真人 KP 同时听几个人说话，
  从不说'你等他说完'"，但它只在**上一轮已结束、锁空闲**时才起作用；上一轮还在
  跑的那 14 秒——恰恰最容易撞上——仍然是硬拒，窗口等于白开。
  另外 `drain(room_id)` 会把窗口里**所有人**的提交一起丢掉，不只这一条。
- **🔴 从 COC 玩家角度定的方向**（用户要求换视角后得出，这条是判据不是实现细节）：
  > **真人桌上不存在"你这句无效、请重说"。** 你说出口的话在空气里，KP 最多说
  > "等一下，我先处理完张三"，但绝不会让你重说一遍。

  因此"拒绝时干脆别广播原话"这个方案**出局**——它只是把 P5.1 要杀掉的
  "一次只肯听一个人"换个更干净的形式再做一遍。
- **修法：排队，而且它比想象的小**——收集窗口**本来就是队列**，只是锁失败时被
  `drain` 清空了。正确形态是：锁被占用 → **不 drain**，让这几条留在缓冲里 →
  当前这轮释放锁时发现缓冲非空 → 直接开下一轮。不是新增队列，是**把窗口从
  "本轮"顺延到"下一轮"**。
- **附带**：措辞从 **error** 改成**回执**。「守秘人正在处理其他玩家的行动，
  请稍候再试」读起来是"你失败了"；「守秘人正在回应其他人，你的话已记下」
  才是桌上那句"我听到了，等我一下"。同一件事，感受完全不同。
- **COC 特有的观察（影响设计取向）**：多人同时对 KP 说的话，绝大多数**不是互斥
  动作**，而是「我也看看」「他刚说了什么」「我在门口盯着」这类，天然该并进同一
  拍——这正是收集窗口在做的事。真正冲突的同时行动（A 开门 / B 锁门）很少见。
  所以设计按"**默认可合并**"来做，串行只是罕见情况的兜底。
- **诚实边界**：排队让语义对了（话不会丢、不用重说），但**不等于体验就好了**——
  第二个说话的人要等「别人那轮 + 自己那轮」。所以 #35 和 #36 是一件事的两半，
  只做 #36 是治标。
- **落地形态**：`_handle_action_submit` 拆成「拿锁 + 连跑多轮的 while」与
  `_run_turn`（跑一轮）。锁失败 → **不 drain**、回 `QUEUED` 回执；持锁的循环每跑
  完一轮回头看缓冲，非空就接着跑下一轮。`finally` 只释放锁、不清缓冲。
  🔴 **循环条件 `is_collecting` 是同步的，到 finally 里 release 之间没有任何
  await**——asyncio 单线程下这就是原子的，不会出现"刚判空就有人塞进来、然后锁
  被释放、而没有人再来处理"的孤儿缓冲。这条别改成带 await 的判断。
- **验收**：e2e「收集窗口」用例改写成断言两条路径**共同**的不变量（不拒、不丢），
  并且**把第四条提交的时机算准**（窗口 2.5s + NARRATOR_DELAY 1s → t=2.8s 时缓冲
  已空而锁仍持有），否则撞不上排队路径 = 等于没测。
  🔴 第一版就是这么写的，变异检验（把修复退回成 drain+拒绝）**没抓到**，才发现
  测试从没走进被测分支；算准时机后变异体立刻变红。
- **状态**：已修复。

### #37（已修复）🔴 两人肩并肩站着却被判成分头——一个位置默认值弄坏了三件事

- **症状**（用户两张截图 + 原话）："两边信息不对等，明明是共同的行动，我在张家豪
  那边都看不到一些消息"；"明明是说的'我们打算直接打他一顿'，但是只有凌铭辉过了
  斗殴检定，张家豪没有"。
- **诊断**（数据说话，三条症状是**同一个根因**）：

  房间 `keeper_state` 实况：
  ```
  玩家位置: 凌铭辉@confronting-corbitt, 张家豪@corbitt-house-exterior
  ```
  日志里每一轮都是：
  ```
  keeper_narration_split groups=[('confronting-corbitt',1),('corbitt-house-exterior',1)] segments=1
  ```

  两人剧情上一直站在一起，系统却判成分头。**根因是 P5.2a 里
  `set_current_node_impl` 只挪"本轮发言的人"**：

  ```
  第 1 轮 张家豪发言 → 张家豪@门外（凌铭辉无条目、回落房间指针 → 同组）
  第 2 轮 凌铭辉发言 → 凌铭辉@门口、房间指针也变门口
                      但张家豪有**显式旧条目**「门外」，不再回落 → 分头！
  ```

  当初写这条的注释是"没发言的人位置不动，否则分头探索时留在别处的人会被隔空传送
  走"。**顾虑本身对，默认方向选反了**——绝大多数时间全队是在一起的，分头才是罕见
  且需要显式表达的（这正是 `moves` 存在的理由）。

  三条症状的因果链：
  1. **张家豪收不到消息** —— 分头 → 分段投递 → 每轮只有凌铭辉那组有人发言 →
     `segments=1` → 张家豪那组不生成叙事 → 他什么都收不到。
  2. **只有凌铭辉掷了斗殴** —— 裁决器读着错误的「各自所在」，它自己的 thinking
     白纸黑字写着：*"张家豪在房子外面，能看到冲突但未直接参与"*，于是只给凌铭辉
     发检定。**不是它不懂"我们"，是它拿到的局面信息就是错的。**
  3. 叙事内容也跟着一起错（"张家豪站在凌铭辉身后"其实是模型在圆场）。
- **修法**：`current_node_id` 挪的是**发言者 + 此刻与发言者同处一地的人**——
  "跟你站在一起的人跟你一起走"。完全用现有数据算得出来、不需要模型额外表达，
  且两头都退化正确：全队同处时全员同行；真分头的那位不在发言者所处的地点，
  自然不动（当初那条顾虑仍然成立）。
- **🔴 判据（长期）**：**给一个"默认值"选方向时，要按最常见的情形选，罕见情形
  用显式表达去覆盖。** 这里罕见的是分头（有 `moves` 可表达），常见的是同行，
  而我把默认值定在了罕见那一侧。
- **附带修的**：裁决 prompt 加规则 1b——「**我们**打算…」「大家一起…」是全体
  在场调查员的行动，checks 要为每一位参与者各写一条，不要只留一个 `player: null`。
  （这一条在 #37 修好之后本来大概率也能对，但集体宣告值得单独钉住。）
- **状态**：已修复。⚠️ **实测当时那个房间的 `玩家位置` 已经是脏的**，重开一局才
  能验证。

### #38（已止血，未根治）叙事凭空要求掷骰：对抗检定在 schema 里无法表达

- **症状**（用户原话）："凌铭辉本该进行的体质鉴定，也没有触发骰子的机制"。
  叙事正文写着「凌铭辉，进行一次体质对抗检定，目标 POT 16」，但界面上从没出现
  掷骰卡片，玩家在等一个永远不来的骰子。
- **诊断**：那一轮日志是 `checks=[] hp_changes=1`——**裁决器根本没发起检定**，
  是叙事阶段自己把检定要求写进了散文。为什么？因为 **`KeeperDecision` 表达不了
  对抗检定**：`CheckRequest` 只有 `skill`/`player`/`reason`，没有"对抗目标值"
  （体质 vs POT 16 这种）。模型想要的东西 schema 里没位置放，就从正文漏出来了。
  这与 exec/17 同族：**表达不了的东西会从叙事里漏出去。**
- **已做（止血，概率性）**：`_NO_PENDING_CHECK_HINT`——本轮没有任何待掷检定时，
  由**代码**强制在 user_content 末尾追加「不得要求任何调查员掷骰」。跟
  `_build_check_boundary_hint` 是同一件事的两半（那个管"有检定时别抢跑"，
  这个管"没检定时别凭空要求"）。
- **未做（根治）**：给 schema 加对抗检定（`opposed` 目标属性 + 目标值来源），
  执行层按 COC7 对抗规则结算。这是真功能，另开。
- **已做（根治，2026-07-31）**：`CheckRequest.opposed = {opponent, value}`。
  `value` 是**百分位目标值 0-100**（COC6 式属性点要 ×5：POT 16 → 80），换算
  由裁决器做——它手里有数据卡，代码手里没有。对手侧同样**服务端权威掷骰**，
  胜负按 `dice.resolve_opposed`：等级高者胜 → 等级同则技能值高者胜 → 仍同
  **判主动方负**（规则书说重掷/KP 裁定；真人在等回复，重掷要多一次往返，
  而"平局维持现状"对防守方有利，写死在代码里不交给模型即兴）。
  越界目标值（0/101）**跳过整条检定并记 issue，不夹紧**——夹紧等于把裁决器
  写错的数字变成一个看似合理的规则结论。结果经 `check.result` 广播，前端在
  骰子气泡里多显示一段 `vs 对手 xx/yy · 胜/负`。
- **状态**：已根治。

### #39（待修）NPC 没有 HP 记账，裁决器给 NPC 扣血一律失败

- **症状**（日志，用户未直接提及）：
  `keeper_decision_issues issues=['HP 变更未执行：找不到玩家「科比特」。房间里的玩家：凌铭辉、张家豪']`
- **诊断**：`adjust_hp_impl` 走 `_resolve_character`，只认房间里的**玩家**。
  但战斗里 NPC 当然会掉血——裁决器很合理地想记，系统接不住，于是 NPC 的伤势
  完全没有状态、只活在叙事文字里，下一轮裁决器无从得知它伤到什么程度。
- **候选修法**：NPC 的运行时状态（HP/形态/态度）需要一处存放。模组 schema 里
  `npcs[].stats` 和 `forms[]` 已经有静态数据，缺的是**对局内的当前值**。
  自然的落点是 `keeper_state` 里一张 NPC 状态表，或者复用事实账本那套 events。
- **已做（2026-07-31，与 #38 同一批）**：`npc_state.py` —— `keeper_state` 里一张
  NPC 状态表，`HpChange.npc` 与 `player` **分开两个字段**（一个字段扮演两个
  角色必出结构性 bug，而且"这名字指玩家还是 NPC"本来就不该靠猜）。
  名字解析走**白名单**（模组 npc id / name / 形态 id/name，全部精确匹配），
  解析不出就报错让上层记 issue、**不新建条目**——凭裁决器随口写的名字建状态，
  下一轮换个称呼就成了两个 NPC。
  数据卡没有 HP 那一行时**不编初始值**（静默兜底会造出一个没有依据的假血条，

### #40（待修）向守秘人提问被当成角色行动

### #41（待修）叙事替未发言的玩家做出行动

### #42（已修）玩家看不见自己刚说的话：前端拿正文文本当去重身份

- **症状**（用户原话）："出现了 bug…我好像都没输入"，截图里连着三条守秘人
  叙事，中间没有任何玩家气泡。
- **诊断**（events 表，17:21:17 / 17:21:34 各一条 `action.submit`，utterance

  （**没有任何事件标识**）——只能靠正文文本对齐去重：`act-text:${utterance}`。
  于是同一句话第二次说，撞上第一次留下的 key，被静默丢弃；玩家以为没发出去，

  受众此刻就算得出来，比窗口关闭后更准）。
- **降级方向是显式的**：`eventId` 缺失时**不去重、直接放行**——重复显示只是
  难看，静默丢弃是永久丢消息（同 exec/19 #34 的教训：被去重跳过的那条永远
  不会再来一次）。
- **变异检验**：拿掉 `action.broadcast` 的 `event_id`，
  `test_repeated_identical_utterance_gets_distinct_event_ids` 转红。
- **状态**：已修复。

### #43（已修）对抗检定：双方都失败时仍判出赢家

- **症状**：`keeper.check` 事件里 `{'rolled': 63, 'target': 60, 'level': '失败',
  'opposed': {'rolled': 62, 'target': 50, 'level': '失败', 'won': True}}`。
  两边都失败，系统却记主动方"胜"。
- **诊断**：`resolve_opposed` 初版只比成功等级的序号 + 等级相同时比技能值。
  于是 `失败(rank 1) > 大失败(rank 0)` 会判赢，两边都失败时"技能值高者胜"
  也会判赢。**COC7 里对抗掷骰失败的一方不可能获胜**，双方都失败就是僵局。
- **🔴 最值得记的一点**：给叙事的文本是「63/60（失败） vs 62/50（失败） → 胜」，
  **叙事模型看懂了这个矛盾，按"失败"写了**（写成玩家被按住）——模型比代码判对。
  自相矛盾的结算文本喂给模型，它会自己挑一个解释，于是**日志与玩家看到的故事
  开始各说各话**，这种 bug 靠读叙事永远发现不了，只能靠读事件表。
- **修法**：`resolve_opposed` 加前置——主动方自己没成功就一定没赢；主动方成功
  而对手失败则赢；双方都成功才进入比等级/比技能值那套。
- **状态**：已修复，含一条复现那次掷骰的测试。

### #44（待修）玩家宣告攻击、裁决器没发检定时，叙事会**替他裁定攻击结果**

- **症状**：玩家说「我抄起手边的东西狠狠砸它」，没有任何 `keeper.check`，

  设想的是打怪物）。单独探针验证过，写明「科比特」时裁决器**正确**发起
  `fighting-brawl`（还带 opposed）。所以这不是裁决器的常规缺陷。

  裁定攻击落空。而 `_NO_PENDING_CHECK_HINT`（#38 的止血）恰恰在教它这么做——
  「需要不确定性时，直接把结果写成既定事实」。这条提醒对搜查/移动是对的，
  **对暴力攻击是错的**：攻击的成败是玩家花技能点买来的权利，不能由叙事赠予或
  剥夺。与 #38 同族：叙事在越权替代裁决。
- **已做（2026-07-31）**，两半：
  1. **正向**：`player_state` 加 `physical_conflict`，prompt 里明说这类动作的
     成败**必须由骰子决定**、本轮几乎总该同时给出格斗/射击/力量检定（常常是
     opposed）。
  2. **兜底**：`_UNRESOLVED_CONFLICT_HINT`——分类命中**且本轮 pending 为空**时，
     代码把 `_NO_PENDING_CHECK_HINT` 整条换掉，要求叙事停在动作即将发生的那一刻、
     用一句世界内的话追问，**绝不许写出打中/打空/被闪开/被制住**。
     两条硬提醒方向相反，只能二选一。
  触发条件是**确定的**（分类 + pending 空），分类本身是语义判断——同 #8 迷茫检测、
  #40 提问的先例。护栏拦掉检定同样算"没裁出检定"，照样兜底。
- **改完的探针结果**（真实 API，4/4）：「扑上去抓住科比特」「抄起手边的东西砸**它**」
  「推开他往走廊尽头走」全部 `physical_conflict` 且带出检定（前两条 fighting-brawl

  spot-hidden，没有误伤。**试玩里那句指代不明的「砸它」现在在主路径上就发出检定了**
  ——兜底那条成了兜底，不是常态。
- **状态**：已修复。

  **明确写了新的「当前场景」而 `current_node_id` 为空**时，把房间级指针与所有
  逐人条目一起清空。裁决器**做对了**（找不到对应节点就留空、不编造 id），
  错在代码把"没说"当成了"没变"。清空后护栏退化到即兴层放行，这是正确行为：
  剧本没写到的地方本来就没有"模组标注的检定点"可言。
  判据必须是"写了新场景"而不是"没给 node_id"——否则每个不提场景的普通轮次
  （对话、检定结算）都会把玩家变成失位。对照用例守着这条。
- **状态**：已修复。
