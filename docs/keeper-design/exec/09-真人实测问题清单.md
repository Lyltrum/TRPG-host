### #1 问"我该做什么"时,KP 复述了之前的剧情而不是给建议

- **模组**:科比特先生
- **症状**:玩家明确问"我该做什么",KP 回复的是重复的前情文字,而不是干脆的建议。
- **诊断**:裁决 LLM 调用**返回了空内容**(重试 3 次仍空),触发兜底决策
  (`agent.py:524` `keeper_adjudicate_fallback`)。"迷茫检测→强制注入引导"这条
  逻辑本身是代码层(`is_player_confused` + `inject_confusion_guidance`),不靠模型
  自觉,正常路径下工作正常(批量质检日志里见过它给出具体方向的案例)。但兜底文案
  (`_FALLBACK_ADJUDICATE_GUIDANCE`:"别编造新剧情,能推进就写行动结果,有障碍就写
  眼前障碍")和迷茫引导("给 1-2 个具体方向")拼在一起时,叙事模型大概率把两者
  揉成了"最安全的选择"——复述已知信息,而不是主动给方向。
- **待确认**:这次裁决为什么返回空(是否与"我该做什么"这类元问题特别容易让
  `deepseek-v4-pro` 的 JSON mode 卡壳有关,还是偶发)。**待复现验证**——需要看
  后续同类提问是否复现同样的空响应。
- **候选修法**(不在本轮改,等问题攒齐一起改):迷茫且裁决走兜底时,不要把
  "别编造/让你重说一遍"这类保守措辞和"给具体方向"的强指令拼在一起——两者语义
  冲突,应该让迷茫引导独占,不掺兜底的保守用语。
- **状态**:✅ 已改(与 #2 同一根因,一并修)——迷茫且裁决走兜底时,不再拼接
  兜底的"别编造/让你重说一遍"文案,直接丢弃只用迷茫引导(`agent.py` 新增
  `is_adjudicate_fallback` 判断)。

### #2 回复文字被硬截断(不是优雅裁切,是话说到一半断掉)

- **模组**:科比特先生
- **症状**:玩家说"行吧,那我想去和科比特先生聊一聊",KP 回复的文字被截断了。
- **诊断**:数据库里这条 `narration.push` 原文只有 **51 字**,结尾停在
  "科比特先生侧身探出，额上"——硬生生断在词中间,没有句号也没有省略号。
  代码里的优雅裁切逻辑(`clip_narration`,句末优先截断 + 补省略号,`max_chars=180`)
  **没有触发**(`keeper_narration_clipped` 日志缺失,因为 51 < 180,判断为"没超长")。
  真正的截断发生在更早一步:`_narrate_prose` 传给 DeepSeek 的
  `max_tokens=280`(`TOKENS_NORMAL`)在模型生成过程中把请求砍断了
  (`agent.py:559`)。
- **🔴 反常之处**:280 tokens 对中文来说正常应该够写出接近 180 字,但实际只写出
  51 字就被砍——token 预算被别的东西吃掉了大半。**最可能的原因**:
  `deepseek-v4-pro`(近期从 `deepseek-chat` 换过来的模型,见 07-28 记忆核实记录)
  本身带推理/思考能力,若默认开启内部推理,那部分 token 也会算进
  `max_tokens` 总预算——模型把预算大头花在"思考"上,只剩一点点用来写可见正文,
  写到一半预算就耗尽了。**这是假设,需要验证**(比如查 DeepSeek 文档确认
  `deepseek-v4-pro` 默认是否带隐藏推理、`usage.reasoning_tokens` 字段能否在
  responses 里读到)。
- **候选修法**(不在本轮改):①如果确认是推理 token 吃预算,要么显式关闭该模型的
  推理模式,要么把 `max_tokens` 预算算法改成"正文预算 + 推理预算"分开计;
  ②给 `_narrate_prose` 补 `finish_reason` 日志,以后一眼能看出是不是被
  `length` 砍断的,不用每次翻数据库。
- **状态**:✅ 已改——实测确认根因(直接调用 DeepSeek API 探针:同样的
  system/user prompt,`usage.completion_tokens_details.reasoning_tokens=77`,
  证实 `deepseek-v4-pro` 默认开隐藏推理且吃 `max_tokens` 预算;加
  `extra_body={"thinking":{"type":"disabled"}}` 后 `reasoning_tokens` 归零、
  正文完整生成)。裁决(`_adjudicate`)和叙事(`_narrate_prose`)两处调用都加了
  这个参数,`narrator.py` 的非 keeper 简单叙事器(`DeepSeekNarrator`)同样加了
  (省 token/延迟)。叙事阶段另外补了 `finish_reason=="length"` 的日志
  (`keeper_narration_hit_token_limit`),以后再被 `max_tokens` 硬砍能一眼看出,
  不用翻数据库。


### #3 叙事正文里直接写出"该掷侦察了"——机制播报泄露进了叙事(新的一类问题)

- **模组**:科比特先生
- **症状**:玩家问"我可以过一下侦查技能吗",KP 描写完场景后,正文末尾直接写
  "该掷侦察了。"——这句话和下方独立的检定卡片("守秘人请求你进行侦察检定")
  说的是同一件事,说了两遍,而且是用機制播报的口吻,不是叙事口吻。
- **诊断**:不是缺规则,是模型没照着已有规则做。发起检定时注入给叙事阶段的
  引导原文是:"由**情境示意**玩家掷骰;绝不编造检定结果,也不要提前描写任何
  要靠这次检定才能获得的信息"(`agent.py:365`)——"示意"要求的是氛围/张力
  暗示,不是直说"该掷 XX 了"这种赤裸的机制播报。查过 `scrub_kp_anti_patterns`
  (正文净化函数),**目前只覆盖两类**:选项菜单(对应质检报告的 `menu_options`)
  和"你可以/如果你"式虚拟挡(对应 `virtual_block`)——**没有任何模式针对
  "机制播报泄露进叙事正文"这第三类失败**,是质检报告四类问题(`too_long`/
  `virtual_block`/`menu_options`/`empty_reply`)之外的新类别,此前没被发现过。
- **候选修法**(不在本轮改):①在 `scrub_kp_anti_patterns` 里补一类模式,识别
  并砍掉"该掷/请掷/进行……检定/该……检定了"这类机制播报句(检定卡片本身已经
  承担"提示玩家该掷骰"这个功能,叙事正文不需要再说一遍);②同时检查这类模式
  会不会误伤正常叙事里合理出现"检定"字样的句子(如 NPC 台词提到"警察会来做
  笔录调查"这种,需要精确到"该/请 + 掷/过 + 技能名 + 检定/了"这种结构,不能
  粗暴按"检定"关键词整句砍)。
- **状态**:✅ 已改,且经真人实测(Claude 自测)复验后又补了一版——`prose_discipline.py`
  新增 `_MECHANIC_ANNOUNCE_SENTENCE` 正则,精确匹配"该/请/需要/得 +
  (你/你们)? + 掷/摇/过一下/来一次/进行 + 短技能名 + (检定)?了?(吧|呢)?"
  这个结构,不按"检定"关键词整句砍——"警察会来做笔录调查""这次调查需要你
  冷静地完成检定"这类合法句子实测不受影响。挂在迷茫轮的 `kept_soft` 循环和
  主循环的 `kept` 循环两处,覆盖两条路径。
  **🔴 第一版只匹配整句,真人实测复验时被真实 DeepSeek 输出打脸**:实际
  出现的是"现在距离近了，你该掷斗殴检定了。"这种**逗号分句里的尾句**形态,
  不是独立整句,整句匹配从头锚定不上,漏网。改成 `_strip_mechanic_announce`
  两层匹配:整句命中就整句丢弃;否则按逗号/顿号切出最后一个分句单独匹配,
  命中就只砍这一段+它前面的分隔符,保留前半句描写和收尾标点。已用真实对局
  复现的原句 + 真机再次验证(后续两轮真实检定对话都不再出现该问题)。
  新增单测:`test_scrub_drops_mechanic_announcement`、
  `test_scrub_drops_mechanic_announcement_in_comma_clause`、
  `test_scrub_keeps_legit_dialogue_mentioning_check`。

### #4 角色卡上的 HP/SAN 数值不随检定结果更新(前端消费缺口,不是 agent 缺口)

- **模组**:科比特先生
- **用户提问**:掷骰判断成功/失败后,HP 和 SAN 值没有实际减少——是不是要设计一个
  单独的工具调用/skill 来执行?
- **诊断**:不需要新工具。查数据库确认这局真实发生过两次变化且都正确落库
  (`keeper.san`:55→54→…→49;`keeper.hp`:10→8,原因"汽车驾驶大失败导致车祸")
  ——后端计算/持久化(`adjust_hp_impl`/`san_check_detail`,`tools.py`)本身没问题。
  缺口在前端有没有把这些数据用起来,而且 HP 和 SAN 是**两种不同性质**的缺口:
  - **SAN(数据有,前端没读)**:`san.check.result` 广播的 payload 里后端已经带了
    `sanRemaining` 字段(`app/dto/ws.py` `SanCheckResultPayload.san_remaining`),
    但前端 `RoomPage.tsx` 处理这个事件时只解构了
    `{playerId, rollValue, sanLoss, result, checkRequestId}`,**没有读
    `sanRemaining`**,也没有调用任何函数把新值写回 `useCharacterStore`——角色卡
    绑定的 `character.derived.san` 因此一直是建卡时的快照。纯前端疏漏,数据早就
    在广播里了。
  - **HP(数据根本没广播)**:HP 变化不走"检定→掷骰→广播结果"这条路径,是裁决
    直接判定伤害后立即执行(`execute_side_effects`),落地方式是把
    "🎲 昵称 · HP a → b" 拼进叙事正文当纯文本广播——**没有任何结构化 WS 事件
    携带新 HP 值**。前端角色卡的 HP 从进房间那一刻就是快照,没有任何机制能更新它,
    连"数据在但没读"都算不上,是协议层缺这个事件。
- **候选修法**(不在本轮改):①SAN 部分改前端,`san.check.result` 处理里读
  `sanRemaining` 并写回角色卡 store,工作量很小;②HP 部分需要给
  `adjust_hp_impl` 生效时补一条轻量结构化广播(类似 `san.check.result` 的模式,
  比如 `character.stat_changed{playerId, hp}`),再让前端接住写回 store——这个
  需要动协议(`app/dto/ws.py` 新事件类型)+ 后端广播点(`ws.py`)+ 前端消费,
  比 SAN 那半个大。
- **状态**:✅ 已改——两部分都按候选修法落地:
  - **SAN**:`character-store.ts` 新增 `updateDerived(roomId, patch)`(核对
    roomId 对得上当前存的角色才写,避免跨房间误写);`RoomPage.tsx` 的
    `san.check.result` 处理解构 `sanRemaining`,是自己的检定时写回 store。
  - **HP**:新增 `character.stat_changed` 事件(全链路:`narrator.py` 新增
    `StatChangeNotice` + `NarrationOutcome.stat_changes` 字段;`tools.py` 的
    `KeeperDeps` 加 `stat_changes` 列表,`adjust_hp_impl` 生效时连同已有的
    `check_results` 文本一起追加结构化通知;`agent.py` 的两处 `narrate()`
    返回都带上 `stat_changes=deps.stat_changes`;`dto/ws.py` 新增
    `CharacterStatChangedPayload`,`export_schema.py` 加进导出清单;
    `controller/ws.py` 新增 `_broadcast_stat_change`,在 `action.submit`/
    `check.roll` 两个 handler 里都广播)。San 不需要这个新事件——它走
    "检定→掷骰→广播结果"这条路,`san.check.result` 已经带 `san_remaining`。
    SDK(`trpg-sdk`)codegen 重跑 + `types.ts`/`room-socket.ts` 手写部分同步
    补上;前端只更新**自己**的角色卡(`targetId === playerId` 才写)。
  - 验证:pytest 237、SDK 单测 9、e2e 26 全绿,ruff/ty/前端 tsc+eslint+build
    均干净。

### #5 战斗检定卡片没有生成——技能名解析失败,不是渲染问题(比 #3 更严重的一类)

- **模组**:科比特先生
- **症状**:玩家宣告"那我要制服他",KP 叙事描写了扭打过程,末尾写"该掷斗殴了",
  但**没有出现任何检定卡片**,对话直接卡在这里,这场战斗从头到尾没有真正掷过骰。
- **诊断**:裁决本身判断完全正确——`keeper_decision` 日志显示
  `checks=['斗殴']`,thinking 写的是"应发起斗殴检定对抗",语义合理。但
  `create_pending_checks` 调 `_resolve_skill_target` 解析"斗殴"时报错:
  `未知的技能/属性名「斗殴」`(`keeper_pending_check_issues` 警告日志)。
  **根因**:COC7 规则表里这个技能的规范名是复合名 `格斗：斗殴`,不是裸词
  `斗殴`;`_resolve_skill_target`(`tools.py:146`)只做精确匹配
  (`wanted in (spec.id, spec.name)`),只硬编码了一条同义词归一(侦查→侦察),
  **没有处理复合名技能的短名匹配**。裁决器/叙事器说人话用短名("斗殴"/"手枪"/
  "生物学"/"船舶")是完全自然的,没人会说"格斗：斗殴"这种规则书写法。
- **🔴 影响面**:规则表里共 **33 个复合名技能**(格斗系 7 个:斗殴/剑/斧/矛/鞭/
  链枷/刀/链锯;射击系 6 个:手枪/步枪霰弹枪/冲锋枪/机枪/弓/火焰喷射器;科学系
  14 个:药学/生物学/化学/物理学/……;驾驶系 5 个:马车/飞行器/船舶/航天器/
  热气球)。**任何一次涉及这些技能的检定,只要模型说短名就会静默失败**——
  失败被 `issues` 吞掉、喂给叙事阶段"自然圆场"(不暴露技术细节),
  于是玩家看到的是叙事写得煞有介事地喊"该掷 XX 了",但检定机制其实从未存在过。
  **这是之前 07-24 组装阶段"B 验证观察"里已经点过名的缺口**(A 类缺口 #6
  "技能名归一摩擦:自由中文短名 vs COC7 复合名"),当时只是理论推测,这次真人
  实测里第一次撞上真实后果——一场战斗遭遇完全没法用骰子解决。
- **候选修法**(不在本轮改):`_resolve_skill_target` 补一层复合名短名匹配——
  裸词能唯一定位到某个复合技能的子类名时(如"斗殴"只对应`格斗：斗殴`一个)
  直接命中;需要考虑歧义场景(比如"驾驶"裸词本身对应 5 个子类中的哪个,不能
  瞎猜,应该报错或者要求裁决器给出更明确的子类)。
- **状态**:✅ 已改——`_resolve_skill_target` 在精确匹配失败后加两层短名
  匹配:①按`spec.name.split("：")[-1] == wanted`找子类后缀唯一匹配,命中
  就直接返回(如"斗殴"→"格斗：斗殴");②后缀匹配多于一个,或裸词命中某个
  大类前缀(`spec.name.startswith(f"{wanted}：")`,如"驾驶"对应 5 个子类)时
  报错并列出全部候选,不瞎猜。新增 2 个单测
  (`test_roll_check_compound_skill_short_name`、
  `test_roll_check_compound_skill_ambiguous_prefix`)。

### #6 机制性内容不该混进守秘人的对话框——应做成系统提示(Claude 自测后用户提出)

- **模组**:科比特先生
- **症状**:用户看到"🎲 压测员 · HP 10 → 9"这类文字出现在守秘人的叙事气泡里,
  提出这类内容不应该在 KP 的对话框里说,而应该像系统通知一样单独展示;即使
  以后变成多人游戏,也只需要能指定某些玩家或全体玩家收到提示即可。
- **诊断**:`agent.py` 里有一段专门把 HP 变化拼进 `narration` 文本末尾的代码
  (`if deps.check_results: ... narration = f"{narration}\n\n{dice_lines}"`),

### #8（2026-07-29 补测，用户要求先想清楚根因再记录）问"我现在该做什么"
KP 只给长段景物描写、没有任何建议——**跟 #1 是同一个症状，但根因完全不同**，
不是偶发，是可复现的正则覆盖漏洞

- **模组**：科比特先生（同一个模组之前 #1 已经修过一次这个症状）。
- **症状**：玩家问"我现在该做什么"，KP 回复一整段第一人称叙事景物描写
  （科比特先生拎包裹出门、地下室灯光、街面恢复寂静……），完整重复/延伸
  前情，但**没有给出任何可执行的方向或建议**。
- **用户的要求**：不要只针对这一次测试改，要想清楚根因。
- **诊断（🔴 已用真实代码复现，根因跟 #1 完全不是同一个）**：
  `is_player_confused()`（`prose_discipline.py`）负责判断玩家是不是在问
  "该干什么"类元问题，判断方式是一组**要求字符严格相邻**的正则，比如
  `r"我该(怎么|做|干)"` 必须"我"和"该"紧挨着才算命中。用户这次打的是
  "我现在该做什么"——"我"和"该"中间插了"现在"两个字，这个正则**匹配不
  上**。实测直接调用这个函数：
  ```
  '我该做什么'        confused=True   （旧样本，能匹配）
  '我现在该做什么'      confused=False  （用户这次实际打的，匹配不上！）
  '现在该做什么'       confused=False  （缺"我"，也匹配不上）
  '接下来该做什么'      confused=False  （"接下来"和"做"中间插了"该"，也断了）
  ```
  也就是说：**"迷茫检测→强制注入引导"这条代码层机制这次根本没有被触发**
  ——不是引导注入了但被兜底文案冲淡（那是 #1 的根因，`is_adjudicate_
  fallback` 判断已经解决），而是判断函数自己没识别出"这是一句元问题"，
  于是这轮请求走的是普通叙事路径，模型没有被强制约束、按自己的本能写成
  了安全的景物描写延伸——这正是整个"代码注入引导"机制原本要防的行为，
  只是这次它没被触发。
- **为什么用户会觉得"比重改前端之前更差"**：大概率不是真的变差了，是
  **这次的措辞（"现在该做什么"）恰好撞进了正则覆盖不到的缝隙**，而
  #1 修复时验证用的措辞（"我该做什么"）恰好没有这个问题。同一类症状，
  两次撞上的是两个不同的漏洞，不能把这次归因成"回归"。
- **🔴 根因定性（用户明确要求想清楚，不要只补丁这一句话）**：这不是
  "少写了一条正则"这种可以补一条了事的问题，是**整个检测机制的结构性
  脆弱**——`is_player_confused`/`is_clear_action_intent`/
  `is_weird_or_meta_utterance` 三组正则全部要求"关键词紧挨着"，而中文
  自然表达里插入"现在/到底/接下来/真的"这类填充词是极其常见的现象，
  任何一条要求严格相邻的正则都会被下一个真实玩家的下一句自然表达绕过。
  **补一条"我现在该做什么"的字面量只能堵住这一句话，堵不住下一句**
  （比如"我到底该做什么"/"那我该做什么"）。
  - **顺带验证：同样的脆弱性也影响 `_ACTION_INTENT_PATTERNS`**（判断
    "玩家在宣告具体行动"，触发"强制推进"引导），不只是迷茫检测一处：
    ```
    '我想去查一下书房'      action=True
    '我现在想去查一下书房'   action=False  ← 同款漏洞
    '我打算现在去开门'      action=True
    '我现在打算去开门'      action=False  ← 同款漏洞
    ```
    `_WEIRD_PATTERNS` 大概率也有同类问题，没有逐条验证，但结构相同，
    应该一并审查。
- **原候选修法（放宽正则，已否决）**：最初设计过把"关键词紧邻"的正则
  放宽成 `.{0,N}` 允许插入填充字符（如 `r"我该(怎么|做|干)"` 改成
  `r"我?.{0,4}该.{0,3}(怎么|做|干)"`），且验证过新旧正负样本都不出错。
  **用户否决了这个方向**：加宽一次只能堵住"已经撞见的这批样本"，正则
  枚举字面量在结构上永远追不上中文口语的开放变体，下一句换个措辞大概率
  又能绕过去——这仍然是"打地鼠"，不是根治。这一判断与本仓库
  `docs/keeper-design/exec/11-待办-叙事纪律泛化.md` 里已经点名的同一类
  问题（"样本驱动的模式匹配，泛化边界不可知"）完全一致，互相印证。
- **最终修法（已实施，见 `docs/keeper-design/exec/13-迷茫检测改用裁决
  LLM自分类-执行规格.md`）**：把"这轮发言是不是迷茫/怪话/明确行动"的
  判断，从正则匹配换成**裁决 LLM 在同一次 JSON 结构化输出里顺手分类**
  ——`agent.py::_adjudicate()` 本来就是一次 JSON mode 调用，已经读了
  玩家原话去判断要不要发起检定，给它的输出 schema（`KeeperDecision`）
  加一个 `player_state: Literal["confused","weird_or_meta",
  "clear_action","normal"]` 字段，模型顺手给出分类，**不增加新的 LLM
  调用、不增加延迟/成本**，而且理解"我现在该做什么"这类语义变体正是
  LLM 该干的事，不是正则该干的事。
  - "代码强制注入引导文案、不靠模型自觉"这条架构原则**完全不变**
    （07-23 已论证过靠 prompt 拽不动模型写作本能）——变的只是
    `confused`/`weird`/`action_intent` 这三个布尔值的**来源**：从正则
    匹配换成模型给出的分类字段。
  - **正则没有被删除**，`is_player_confused`/`is_clear_action_intent`/
    `is_weird_or_meta_utterance` 三个函数原样保留，只在裁决**完全失败**
    （走 `_FALLBACK_ADJUDICATE_GUIDANCE` 兜底、此时 `player_state` 只是
    不可信的默认值 `"normal"`）时才退回正则作为兜底安全网——这个分支
    极少触发，且此时模型本身已经不可用，正则聊胜于无。
  - 新增 `trpg-backend/tests/test_keeper_agent_player_state.py`，用真人
    实测撞见的原句"我现在该做什么"直接写成回归测试：先断言

    更有说服力。另外三条测试覆盖：裁决完全失败时退回正则兜底、
    `player_state="normal"` 时三个分支都不触发（回归保护）、
