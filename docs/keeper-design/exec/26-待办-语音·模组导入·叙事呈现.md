## 62 · 叙事呈现：思考中提示 + 前端打字机

### 现状：指示器有，但它一个字都没有

`RoomPage.tsx` 里已经有 typing indicator——📜 头像 + 三个 bounce 的点。问题是
**没有文字**：

- 三个点是聊天软件的通用符号，但它撑不住 **9.5 秒**；
- 玩家分不清「它在想」和「卡死了」，也不知道还要等多久。

🔴 这跟 `exec/23` 那条教训同族：**队友角色卡（P5.3）代码完整，但入口是顶栏一个
无文字的小图标，真人实测直接反馈「没有实现」。** 无文字的符号在这个产品里已经
翻过一次车。

### 两件事的分工（别混为一谈）

| | 解决什么 | **不**解决什么 |
|---|---|---|
| 「守秘人正在思考」文字提示 | 等待期间不知道在发生什么 | 等待本身 |
| 前端打字机 | 一大段文字砸下来、临场感 | **首字延迟**（还是 9.5 秒后才开始打） |

打字机有一个附带收益：等待结束后还有 4–5 秒有内容在动，注意力被接住，**9.5 秒
会显得更短**。不改任何数字，但它是感知延迟里最便宜的一段。

### 实现要点（前三条是真坑）

1. 🔴 **重连/历史回放不能重新打字一遍。** 刷新页面后把整局叙事重打一遍，玩家
   会疯。只有**新到的那一条**打字——判据挂在 `seenEventKeysRef` 那套事件去重上，
   也就是 `exec/19 #34` 的教训所在地。
2. 🔴 **打字开始就解锁输入，不是打完才解锁。** `exec/23 #58` 刚把输入锁到叙事
   到达为止；改成"打完字才解锁"等于又加几秒锁定，比现在更糟。**文本到了这一轮
   就结束了，打字只是渲染。**（同族提醒：改了时序就要回头查依赖旧时序的代码。）
3. **必须可跳过**——点一下立即全显示。
4. 检定卡片、掷骰结果**不打字**：那是机制信息，要立刻看到。
5. 打字中又来一条叙事（掷骰拆两拍的结算）→ 排队，不能叠着打。
6. 速度：中文 30–40ms/字，一段 130 字约 4–5 秒。太慢比不打字更烦。

## 63 · 模组导入：把任意模组转成 structured

### 现状：这是接线，不是从零

查证下来比预想的近得多：

| 部件 | 状态 |
|---|---|
| `POST /modules/import`、`GET /modules/import/{jobId}` | 端点在，`start_import` 是 **NOT_IMPLEMENTED** |
| `module_import_jobs` 表、`ModuleImportJobRead` DTO | 都在 |
| 预处理管线（裸抽取探针 → 关系发现 → 组装 → `validate_module.py`） | **`scripts/module_probe/` 里是完整的**，`exec/02`–`07` 做的就是这个 |

缺的是：把命令行管线包成异步任务 + 上传/进度 UI。

### 为什么这条方向是被认可的

CLAUDE.md 的 agent 判据：**有便宜可靠的验证器 → agent 划得来；没有 → workflow。**
主持人回合归 workflow，而**模组预处理才是这个项目真正的 agent 命题——
`validate_module.py` 就是编译器报错**。这条待办正落在那个判断上。

它也是「这是个 5 模组的 demo，还是一个平台」的分水岭。

### 两个已知风险

1. **质量不稳。** 契约 v3 的实测：关系稳定天花板 **73%**，容量是关系发现的瓶颈、
   必须分批。所以**导入完必须把 validate 报告给用户看**，不能假装导完就能玩。
   大模组整份 LLM 自修易截断，引用类错误优先机械修（`assemble.py` 已有这套）。
2. 🔴 **版权。** 用户导入的模组正文落**数据库**可以，但**绝不能**进 git 跟踪
   文件、commit message、日志、评测报告。导入功能会让第三方正文第一次大量流经
   系统，这条红线的暴露面比现在大得多。

## 64 · 语音播报

### 先回答一个设计问题，再谈技术选型

🔴 **叙事已经是 per-audience 裁剪的（`exec/14 P5.2d`），而语音是公共信道。**

分头时两边收到不同文本。如果都念出来，隔壁桌当场听见——辛苦做的裁剪在音箱面前
直接失效。这不是"注意一下"的问题，是**功能的前提**：

> 「哪些内容可以念」必须先定死。倾向：**只念 `audience=None` 的公开叙事，
> 私密段落一律不念。**

同族判据：受众算错必须表现为**没人听见**，绝不能退化成"全桌都听见"。

### 谁的设备在念

多人同桌时每人手机都念会重叠。这直接连到 Obsidian
`思考/线下形态-桌面主持台与N+1设备` —— **语音天然属于公共渲染**，该只在主持台/
房主设备上播。

### 依赖

**依赖 62 的前置形态**（或真流式）。现在叙事一次性返回，等 9.5 秒再合成音频，
比纯文字更慢。

### 技术选型（未定，可以晚点再说）

| 方案 | 优 | 劣 |
|---|---|---|
| 浏览器原生 `SpeechSynthesis` | 免费、本地、零网络延迟 | 中文音质一般，音色不可控 |
| 云 TTS | 好听、可选音色 | 要钱、加一次网络往返 |

## 🔴 附：被推翻的方案 —— 真流式输出（按 token 推）

第一版提的是标准流式：LLM 边生成边推给前端，逐 token 显示。**推翻了**，理由要
留住，免得以后有人（包括我）再提一遍。

### 它会把一条**代码强制**降级成概率性的

`prose_discipline` 的叙事纪律层是**拿到完整文本后用正则删**：

```python
body = _BRACKET_MENU.sub("", body)            # 方括号菜单
body = _MENU_TAIL.sub("", body)               # 「你可以：…」菜单尾巴
body = _PARENTHESIZED_MECHANIC.sub("", body)  # 括号里的机制播报（exec/19 #45）
_SENTENCE_DROP ...                            # 按句砍
clip_narration(...)                           # 超长截断
```

**流式 = 字已经在玩家屏幕上了，删不掉。** 这是本项目少数几条真正「代码强制」的
防线之一，真流式会把它变成「大概率不会出现」——正是 `exec/20` 那份清单在管的
那类退化。

用一个已经硬掉的保证去换感知延迟，不划算。

### 替代方案（用户提出，已采纳为 62）

> 后端照旧把整段文本处理完（纪律层全跑），**前端拿到之后再逐字显示**。

- 纪律层零损失；
- 架构一行不用动（协议、`eventId` 去重、两阶段回合制全不受影响）；
- 代价：**不降低首字延迟**——但那部分由「思考中」提示接住。

### 附带记录：按句/按段推的中间方案

也评估过「生成到句号边界才推一段，纪律层按句判断」：首字延迟 ~1.5–2s，纪律层
保留大部分。**但跨句规则会漏**（菜单尾巴通常长在结尾，发现时已经推出去了），
而且要改协议、改前端去重。**收益不足以抵消复杂度**，同样不做。

另注：**裁决那一拍本来就不能流式**（JSON mode 要完整 JSON 才能解析），任何
流式方案都只能作用在叙事那一拍上。
