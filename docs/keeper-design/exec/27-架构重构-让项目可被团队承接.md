# 27：架构重构 —— 让这个项目可被团队承接

> 2026-08-01 立项。**当前最高优先级，其余待办（exec/26 的语音/模组导入/叙事呈现、
> 前端 UI v2）全部排在它之后。**
>
> 起因：用户指出「我一个人做」是当前**工作方式**，不是**架构目标**。这个项目
> 应该能被一个团队承接并合理分工，而这是产品的**非功能性属性**（同可测试性、
> 可观测性），必须内建，不能等人来了再改造。

## 一、判据

单一判据，所有设计决策都对着它检验：

> 🔴 **一个新人能不能只读一个目录，就完成一个功能——而不必理解整条链。**

现在的答案是**不能**：加一个守秘人能力，他得同时读懂并修改
`decision.py`(schema) + `prompts.py`(教模型) + `tools.py`(执行) + `agent.py`(接线)
四个文件，还得知道它们为什么必须一起改。

两条支撑理由（用户提出，已采纳）：

1. **等到有人来了再改就改不动了。** 架构债是复利的：`agent.py` 现在被 46/90 个
   功能碰过，再长半年可能是 60/120，那时拆它的风险与工作量不是一个量级。
2. **这是自我实现的预言。** 个人项目形态的架构**本身就是接手门槛**——没人能快速
   上手，于是永远只能一个人做，于是永远"不需要"为多人设计。循环必须从架构这头断。

## 二、现状测量（不是印象，是数据）

### 依赖结构：健康，只有一条坏边

```
循环依赖 5 组，全部经过同一条反向边：core.narrator → core.keeper.agent
移除它之后：0 组
```

`keeper/` 内部本来就是干净的 6 层 DAG：

```
L0  catalog chapter decision dice history module_loader pending phase
    prose_discipline scene_state sheet_digest skill_names
L1  agenda_state check_guard fact_ledger leak_guard location_state
    npc_state prompts subject visibility
L2  tools    L3  turn_executor    L4  agent    L5  heartbeat
```

**层次是清晰单向的，问题是目录一个字都没表达它**——25 个文件平铺。

`narrator.py` 现在同时是抽象层（`Narrator` ABC + 数据契约）、工厂
（`build_narrator` 要构造 `KeeperAgent`）和一个实现（`RoomAwareKeeperNarrator`）。
抽象反向依赖具体，现在靠**三处函数内 import** 硬撑——那是绕过循环，不是消除。

### 并行开发：这才是真瓶颈

git 历史（2026-07-20 起，90 个碰后端源码的 commit）：

| 指标 | 值 |
|---|---|
| 平均一个功能改几个源文件 | **4.1**（中位数 4） |
| `core/keeper/agent.py` 被多少功能碰过 | **46 / 90** |
| `prompts.py` | 29 |
| `controller/ws.py` | 22 |
| `tools.py` | 21 |

最常一起被改的文件对：

```
25次  agent.py + prompts.py        17次  decision.py + prompts.py
18次  agent.py + tools.py          17次  ws.py + agent.py
16次  agent.py + narrator.py       15次  prompts.py + tools.py
```

**两个人随便做两个 keeper 功能，一半以上概率撞在同一个文件上。**

### 🔴 由此得出的关键结论（推翻了第一版方案）

按技术层分目录（`contract`/`rules`/`state`/`memory`/`access`…）**不会改善并行开发，
反而更糟**：一个功能天然横跨四层，按层分只会把"改一个功能跨 4 个文件"变成
"跨 6 个目录"。

活样本是 `exec/25 #59`：加一格分类，改了 `decision`(schema) + `prompts`(定义) +
`prose_discipline`(guidance) + `agent`(分支)。**这不是文件放错地方，是能力被按
技术层切碎了。**

## 三、终态：按能力垂直切

```

│   ├── decision.py            KeeperDecision：由各能力的字段片段组装
│   ├── module.py              ScenarioModule 剧本数据

│   ├── dice.py                1d100 · 成功等级 · 大成功/大失败
│   └── skills.py              技能 id 白名单（原 skill_names）

├── capabilities/          🔴 一个能力一个目录，新人只读这一个
│   ├── skill_check/           技能检定
│   │   ├── schema.py              CheckRequest / OpposedTarget
│   │   ├── prompt.py              教模型什么时候发检定
│   │   ├── executor.py            create_pending_checks
│   │   ├── guard.py               check_guard（模组标注护栏）
```

**验收：加一个新能力 = 新增一个目录 + 在 registry 注册，不改 `runtime/` 一行。**

### 能力清单为什么是这 9 个（判据）

> **一个能力 = 一组「历史上总是必须一起改」的东西。**

用共变更验证边界：`exec/19 #38`（对抗检定）完整落在 `skill_check`；`#39`（NPC 扣血）
完整落在 `health`；`#37`/`exec/25 #60`（位置、带人移动）完整落在 `movement`。

反例同样重要：`exec/25 #59`（加 `feasibility_question` 分类）**跨不进任何能力**
——它改的是 `player_state` 分类与代码强制，那属于 `runtime/`。这条反例证明了
`runtime/` 该独立存在。

### 🔴 `checks` 为什么必须拆成三份

第一版把检定整块叫 `checks`，用户指出"名字太大"。拆开后发现根因不是名字，是它
把**共享机制**和**能力知识**混在了一起：

| 内容 | `skill_check` 用 | `san_check` 用 | 归属 |
|---|---|---|---|
| 掷骰 + 成功等级 | ✅ | ✅ | `primitives/dice.py` |
| 两段式待掷队列（`kind="skill"｜"san"`） | ✅ | ✅ | `runtime/pending.py` |
| 技能 id 白名单 | ✅ | ❌ | `primitives/skills.py` |
| `CheckRequest` schema + 护栏 + 发起 | ✅ | ❌ | `capabilities/skill_check/` |

前两行若留在 `capabilities/checks/`，`san_check` 就得 import `skill_check`——
而**阶段 0 架构测试的核心断言之一正是「能力之间不许互相 import」**，会当场变红。

> 用户凭手感说"太大"，架构测试会在代码里抓到同一件事。**手感与机器判据指向同一
> 条边界时，那条边界大概率是真的。**

### registry 的八个钩子

一个能力向系统注册八样东西。**第一版设计只想到前三个，后四个全是切到某一片
时在真代码里被撞出来的**——这条规律比清单本身更有用：

| 钩子 | 作用 | 例（health） |
|---|---|---|
| `schema` | 往 `KeeperDecision` 贡献字段片段 | `hp_changes: list[HpChange]` |
| `prompt` | 往裁决指令贡献一个块（带显式 `order`） | 规则 9 |
| `executor` | 往执行阶段贡献处理函数 | `adjust_hp_impl` / `adjust_npc_hp_impl` |
| **`situation`** | **往「局面块」贡献要喂给模型看的状态** | `format_npc_states`（NPC 血量） |
| **`audit`** | 往结构化日志与 `keeper.decision` 事件贡献留痕字段 | `hp_changes=2` |
| **`reserved_state_keys`** | 声明自己在 `keeper_state` 里占的键 | `NPC状态` |
| **`pending`** | 两段式玩家掷骰·**发起**：把裁决解析成待掷记录 | `create_pending_skill_checks` |
| **`settle`** | 两段式玩家掷骰·**结算**：玩家点了之后怎么掷 | `settle_skill_check` |

第四个钩子是 `agent.py:383` 那行 `format_npc_states` 暴露的——**能力需要让模型
看见自己的状态**，否则模型不知道谁快死了。

第五个是 `agent.py` 那行 `logger.info("keeper_decision", ...)` 暴露的：它逐个
列出每个能力的字段，不抽钩子的话「加一个能力不改编排层一行」当场不成立。
而且**漏了不会报错**，只是那片能力从此在日志里隐身——线上排查时看不出它本轮
做没做事。两个钩子同一个来源：**编排层每一处"逐个列出各能力字段"的地方，
都是一个还没被发现的钩子。**

## 三之二、三处撞名一起理顺

`stealth`（技能）/ `stealth`（状态）/ `visibility`（线索）三个名字互相干扰，是
"读不懂"的一个具体来源。改名代价分层：

| 改什么 | 代价 | 结论 |
|---|---|---|
| 技能 id `stealth` | **不能改**——COC7 规则表，规则权威（`exec/17` 刚 id 化） | 保留 |
| 模块名 / 目录名 | 零 | 改 |
| `KeeperDecision` 字段名 | 改 prompt + 重录磁带 | 中，值得 |
| `ScenarioModule.visibility_pairs` | **五个模组的 structured.json 要迁移** | **不改** |

```
技能 stealth（角色卡上的能力值）   → 不动，它是规则
decision.stealth                  → hiding          「此刻藏着没」
模块/目录 visibility              → clue_reveal     「线索揭示」
decision.visibility_revealed      → clues_revealed
ScenarioModule.visibility_pairs   → 不动（模组数据，"配对表"本身不歧义）
```

改完读起来不会再混：

```python
checks: [{"skill_id": "stealth"}]              # 掷潜行检定（能力值）
hiding: [{"player": "阿铁", "hidden": true}]    # 他藏起来了（状态）
clues_revealed: ["pair-3"]                     # 线索揭开了（信息）
```

**不单独开一轮**：改名要重录磁带，跟对应能力的切分合并做，只重录一次。

## 四、障碍（都是真的，不装作不存在）

| # | 障碍 | 处理 |
|---|---|---|
| 1 | `KeeperDecision` 必须是**一份**整体 schema（LLM 的 JSON schema 不能分片） | 各能力提供字段片段，组装期用 pydantic 动态建模合并。**顺序要稳定**，否则 schema 抖动 |
| 2 | prompt 是一整段文本，且**块的顺序有语义**（规则 1–12 编号） | 注册时带显式 `order`，不靠字典序或 import 顺序 |
| 3 | 🔴 `agent.py` 里那条 if/elif 链的**顺序就是语义**（`kp_question` 优先于 `confused` 优先于…），拆错会**静默**改变行为 | **动手前先写表征测试**（characterization test）把当前分支行为逐条钉死，再拆 |
| 4 | prompt 一改，磁带请求指纹漂移 | 重录 `tests/tapes/keeper_minimal.json`；真实模组磁带本来就 gitignored。⚠️ 原文写「digest 全漂、磁带集体作废」**不准确**：磁带是**按序回放**的，穿得过 prompt 变化；真正要求重录的是 `test_keeper_replay` 里那条 `assert drifts == []`（它守的是"上下文组装没变"）。所以只在**故意改 prompt 文本**时重录，纯搬运不必 |
| 5 | `tools.py` 961 行、`agent.py` 1413 行要拆散重组 | 分阶段，每阶段末系统必须完全可用 |

### 阶段 0/1 的落地记录（2026-08-01）

**阶段 0** — `tests/test_architecture.py`：AST 扫全部 `app/`，三条断言（无新增
循环 / 跨层不反向 / 豁免只能变短）。扫描用 `ast.walk`，**函数体内的延迟导入照样
算**——那正是当年绕过循环用的写法。

两个当场的收获：

- **测试第一次跑就抓到一个手工分析漏掉的环**：`tools.py` 的
  `from app.core.keeper import dice` 走了包，而 `keeper/__init__.py` 里
  re-export 了 `KeeperAgent`，于是 `tools → 包 → agent → tools`。之前的临时脚本
  把 `__init__.py` 算成了不存在的 `...keeper.__init__` 节点所以漏了。
  **正式测试比临时脚本可靠。**
- **分层定义第一版是错的**：`app.core` 里混着基础设施（`db`/`errors`/`config`/
  `logging`，最底层）和领域逻辑（在 `models` 之上）。没分开时把
  `from app.core.db import Base` 误判成 6 处违规。真违规只有
  `heartbeat → service.{action_lock,ws_manager}` 两条，已列入豁免待修。

变异检验四条全部按预期变红，且**各只红对应的那一个测试**：顶层 import 新循环、
函数体内延迟导入、跨层反向、修好豁免却没删清单。

🔴 过程中踩了一次自己记过的坑：变异脚本中途 `IndexError` 退出，**复原语句没执行**，
把一个变异体留在了 `models/event.py` 里。复原必须与施加同样精确，而且脚本崩了
复原就不会跑——重写的版本用 `try/finally`。

#### 验证方式：prompt 逐字节比对

**一、`parents[N]` 数层数，症状是一条用例静默 skip。**

> **迁移是历史记录，但它引用的应用代码是活的。** 模块搬家时坏掉的地方离你改的
