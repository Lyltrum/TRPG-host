# 20：概率性改进清单 —— 哪些地方还在"请模型配合"

> 用户 2026-08-01 要求单独立此清单：**最终版本可能把这些改成硬编码 / 硬条件，
> 做成真正的实现。** 本文件是那次改造的输入。
>
> 判据（项目 CLAUDE.md 已有）：**能用代码确定性判断触发条件的，一律代码强制；
> 纯语义判断只能靠 prompt + 可观测日志，如实说明是概率性改进，别假装能保证。**
> 这份清单就是"还没能力做成硬的"那一半的全集。

## 怎么读这张表

每一条分三层看：

| 层 | 含义 |
|---|---|
| **触发条件** | 什么时候注入/生效。**代码判定**=确定；**LLM 判定**=概率 |
| **执行方式** | 注入之后靠什么起作用。**代码改数据**=确定；**prompt 请求**=概率 |
| **验证手段** | 有没有可变红的守门人 |

一条改进只要**任意一层是概率的**，整条就不是保证。当前大部分条目卡在
"执行方式"这一层：触发条件已经代码化了，但最终动作是"在 prompt 末尾请它别写"。

## 一、执行方式是概率的（触发条件已确定）

这一组的共同形态：**代码算准了该不该提醒、提醒谁、提醒什么，但提醒本身仍是
一段自然语言，模型可以不听。** 硬化方向是把"请你别写"换成"你写了也没用"
（结构上拿不到 / 写了会被结算层否决）。

### 1.1 `_NO_PENDING_CHECK_HINT`（agent.py）

- **触发**：代码判定 —— 本轮 `pending_checks` 为空。
- **要求**：正文不得要求任何调查员掷骰。
- **为什么会犯**：裁决器想要的东西 schema 表达不了（exec/19 #38 的对抗检定），
  就从散文里漏出去。
- **硬化方向**：schema 补全表达能力（#38 的 `opposed` 已经补上一类，
  剩下的按同样方式补）；或者叙事产出后做一次结构化后检——正文出现"检定/掷骰
  祈使句"且本轮无 pending 时**整句删除**（现在只删了几种固定句式，见 1.6）。

### 1.2 `_UNRESOLVED_CONFLICT_HINT`（agent.py，exec/19 #44）

- **触发**：代码判定 —— `player_state == "physical_conflict"` **且** pending 为空。
  （分类本身是 LLM 判的，见 2.1。）
- **要求**：不得写出攻击的成败，停在动作发生前并追问。
- **硬化方向**：真正的硬做法是**让这一轮根本产不出"结果"**——比如把攻击轮拆成
  「宣告 → 确认 → 结算」三段协议，未确认时叙事阶段拿不到任何可以写成结果的
  数据。现在是同一段叙事里请它自己刹车。

### 1.3 `_build_check_boundary_hint`（agent.py）

- **触发**：代码判定 —— 本轮有 pending 检定。
- **要求**：不得预支检定结果（两个维度：信息 + 动作本身已在成功进行）。
- **为什么难硬化**："这段话有没有替检定预支结果"是语义/因果判断，没有可靠的
  代码判据。当前只有 `keeper_check_pending_narration` 日志做可观测性。
- **硬化方向**：唯一可能的结构性做法是**分两次生成**——检定发起那一轮的叙事
  只允许写"情境"，结果段等掷骰后再生成（代价是多一次 LLM 往返）。

### 1.4 `_build_bystander_hint`（agent.py，exec/19 #41）

- **触发**：代码判定 —— 按每段受众算出本轮没发言的人，名单是确定的。
- **要求**：不得替他们写主动动作/观察/台词。
- **硬化方向**：无法从生成侧硬保证（模型知道名单才能不写他们，知道了就可能写）。
  可做的是**产出后检测**：正文出现"沉默者姓名 + 主动动词"时打回重写一次。
  代价是一次额外往返，且"主动动词"本身又是语义判断。

### 1.5 段尾【投递范围·代码硬提醒】（agent.py `_narrate_per_audience`）

- **触发**：代码判定 —— 分头/隐匿/私密时按受众分段。
- **要求**：只写这一处的事。
- **现状说明**：P5.2d 之后这条**已经降级为文风要求**，不再承担保密职责——
  保密改由 `view(audience) → situation` 结构性保证（历史/账本/原话三处一起裁）。
  留在这里是因为它仍在影响文风，但它已经不是安全边界。**这条不需要硬化。**

### 1.6 `prose_discipline` 的各类 scrub（事后删除）

- **触发**：代码判定 —— 正则匹配。
- **性质**：**这一层本身是确定的**（匹配到就删），概率性在于**正则覆盖不全**：
  已知漏过两次（"该掷斗殴了"整句形态 → 补；`（请进行理智检定，0/1d4）` 括号
  形态 → exec/19 #45 补）。每次都是真人/试玩撞见才补上。
- **硬化方向**：与其穷举句式，不如让"机制播报"在结构上无处可写——参见 1.1。

### 1.7 `inject_*_guidance` 系列（prose_discipline.py）

`inject_confusion_guidance` / `inject_weird_response_guidance` /
`inject_action_resolution_guidance` / `inject_scene_transition_guidance` /
`inject_spotlight_guidance` / `inject_kp_question_guidance`

- **触发**：代码判定（分类命中 / 场景指针变化 / 谁最久没被点到）。
- **要求**：都是"请你这样写"的自然语言指引。
- **硬化程度分级**：
  - `inject_kp_question_guidance`（#40）**已经半硬**：同时代码强制清空了
    `checks`/`san_checks`/`moves`/`current_node_id`，"推进世界的手段"是真被
    收走的，剩下的才是文风请求；
  - 其余几条**纯 prompt**。

### 1.8 「调查员的过去归玩家」（exec/23 #55）

- **触发条件**：代码判（`player_state == "question_to_kp"` 时注入；system prompt
  那节则是常驻）。
- **执行方式**：请模型别编——**概率性**。
- **已经硬掉的那一半**：角色卡（职业／技能／背景／HP·SAN）进局面块是代码
  注入，空背景显式渲染成「未填写」。**模型看不到的东西编不出来**这条在这里
  不成立（它可以凭空编），但"卡上写了什么"现在是确定的，编造与卡冲突时至少
  可以被人一眼看出来。
- **硬化方向**：难。判断"这段话是不是在给玩家安一段没依据的过去"是纯语义。
  真要硬化只能换方向——**让卡上真的有背景**（见 exec/23 #55 末尾两条候选），
  从源头消灭空白。

## 二、触发条件就是概率的（LLM 判定）

这一组的共同形态：**分类由裁决 LLM 给出**，代码只是消费它。分类错了，
后面所有代码强制都作用在错误的前提上。

### 2.1 `player_state` 六分类（decision.py）

`confused` / `weird_or_meta` / `clear_action` / `question_to_kp` /
`physical_conflict` / `normal`

- **为什么归 LLM**：exec/13 已经论证过——正则做中文语义分类有结构性上限
  （"我该做什么" vs "我现在该做什么"，插一个词就匹配不上）。
- **可观测性**：每轮 `keeper_decision` 日志都记了分类结果，可以事后统计。
- **硬化方向**：分类本身不可能硬化（它就是语义判断）。能做的是**降低误分类的
  代价**——像 `question_to_kp` 那样，命中后走的动作全部代码化、可回滚。

### 2.2 `skill_id` 白名单的守规率（exec/17 (B)）

- **现状**：DeepSeek 走 **JSON mode**，不是带 schema 的 structured output，
  `enum` **约束不到生成**，只能 prompt 给表 + 代码校验。模型写中文名时走显式
  回退并打 `keeper_skill_id_fallback` warning。
- **实测**：探针 4/4 守规（含复合名 `fighting-brawl`）。
- **硬化方向**：**这条有明确的硬化路径**——换成支持 structured output /
  json_schema 的调用方式，enum 直接约束解码。届时回退路径可以删掉、改成硬失败。
  这是清单里最接近"可以真正硬化"的一条。

### 2.3 对抗检定的目标值换算（exec/19 #38）

- **现状**：COC6 式属性点（POT 16）要 ×5 换算成百分位，**换算由裁决器做**
  ——数据卡在它手里，代码手里没有。代码只能挡住 0/101 这种明显越界。
- **风险**：没换算（直接填 16）代码挡不住，16 是合法百分位。
- **硬化方向**：把 NPC 数据卡结构化（`stats` 现在是自由 dict），代码就能自己
  查表换算。属于"模组 schema 再进一步"的工作。

### 2.4 `hp_changes` 的 `npc` / `player` 分流（exec/19 #39）

- **现状**：写哪个字段由裁决器决定。名字解析走白名单（解析不出报错、不新建），
  但**"这个名字指的是玩家还是 NPC"仍是它判的**。
- **硬化方向**：两边都是白名单，代码其实可以自己判——把 `player`/`npc` 合并成
  一个 `target` 字段 + 代码查表决定它属于哪一类。**这条可以硬化。**

### 2.5 结局收束 `ending_reached`（exec/19 #47）

- **现状**：`format_endings_status` 把结局与触发条件摆进局面块每轮可见，但
  "这段剧情算不算命中结局"是纯语义判断。
- **硬化方向**：只有把 `trigger` 从自由文本改回结构化条件才可能代码判定——
  而 exec/04 已经**实测推翻过**这条路（三枚举从一个模组倒推、归错就废）。
  **判断：这条大概率永远是概率性的**，不要为它设计硬条件。

### 2.6 议程触发 `agenda_fired`

- 同 2.5：`trigger` 是自由文本，触发判断归模型。代码只做 id 合法性 + once 去重。
- 区别是议程有「议程状态」小节常驻，实测触发率明显好于结局。

### 2.7 隐匿解除的另外两件事（exec/19 #46）

- **已硬化**：离开该地点 → 代码解除。
- **仍靠自觉**：被发现 / 主动现身。
- **硬化方向**：「被发现」其实可以挂在检定上（潜行对抗失败 → 自动解除），
  **这条可以硬化**，只是要先有"潜行是对抗检定"的表达。

### 2.8 AI 玩家的「不主导、不越权」（exec/21 第三层）

`ai_actor.py` 的 `_INSTRUCTIONS` 里六条规矩，全部是 prompt 约束：

| 规矩 | 是概率的还是硬的 |
|---|---|
| 不主导、不替别人做决定 | **概率**——纯语义，代码判不了"这句话是不是在指挥别人" |
| 只说自己做什么、不描述结果 | **概率**——但即使它写了结果也不生效：世界状态只有守秘人的执行阶段能改 |
| 只用知道的信息、不编地名人名 | **概率**——不过它的上下文里**本来就没有**剧本（结构性），能编的只是凭空捏造，不是泄密 |
| 不掷骰、不报数值 | **硬**——它的输出只有一句自然语言，没有任何写状态的字段 |
| 沉默是正常选项 | **概率**（`act` 字段由它自己填） |
| 一句话不超过 40 字 | **硬**——`_UTTERANCE_MAX_CHARS=60` 代码硬裁 |

- **实测方式**：每轮 `ai_player_intent` 日志记了 `act` 与 `thinking`，可事后统计
  它开口的频率与理由。
- **硬化方向**：「不主导」大概率永远硬不了，它本质上是文风问题。真要压制，
  可行的是**代码层限流**（例如"连续 N 轮真人没说话才允许它开口"），把频率变成
  代码判据，而不是继续加 prompt。
- 🔴 **不要"修"它走弯路**：有限视角必然导致它查错方向、重复搜同一个地方。
  那是设计代价不是缺陷，一修就滑向全知提示机。

## 三、结构上已经硬了的（对照组，别误当成待办）

列出来是为了**划清边界**——下次说"这里靠不靠谱"时，能一眼看出哪些已经不需要
担心了。

| 事项 | 为什么是硬的 |
|---|---|
| 掷骰点数 | `dice.py` 掷，LLM 只消费结果 |
| HP / SAN 记账 | 纯代码写库，LLM 改不了 |
| 事实账本 L1 | 代码记账（`fact_ledger`），不靠模型写 keeper_state |
| per-observer 投递 | 另一组的 socket **收不到字节** |
| per-audience 上下文（P5.2d） | 历史/账本/原话三处按受众裁，**模型拿不到就漏不出来** |
| AI 玩家的有限视角（exec/21 L3） | 它的上下文里没有 `ScenarioModule`，历史过 `visible_history(audience={自己})`；**签名里根本没有剧本参数** |
| 检定护栏 | 模组白名单 id 集合比较（战斗轮豁免，exec/19 #49） |
| NPC / 节点 / 议程 / 密级 id | 白名单校验，未知 id 拒绝写入并记 issue |
| 位置与分组 | `location_state` 代码算，含"同处者跟着走"（#37） |
| 元层泄密 | `leak_guard` 连续 14 字逐字重合，命中即整句丢弃 |
| 收集窗口 / 行动锁 | 纯代码时序 |

⚠️ 一条容易混淆的：`leak_guard` **只守 meta 层**。虚构内线索（diegetic）
"未挣得就说出来"仍然只能靠 `narration_guidance` 约束——那部分属于第一类。

## 四、如果要做"真正的实现"，建议的优先级

1. **2.2 structured output**（换调用方式即可，收益直接：skill_id 变成真 enum）
2. **2.4 `target` 字段合并 + 代码查表**（改动小，消灭一处 LLM 判断）
3. **2.7 潜行对抗化**（顺带把"被发现"变成检定结果的副作用）
4. **1.1 / 1.6 合并处理**：与其补正则，不如补 schema 表达力 —— 每补一类，
   对应的"请你别写"就可以删掉一条
5. **1.3 分两次生成**（代价最大，收益也最大：检定抢跑是从 exec/09 一直复发到
   现在的老问题）

**不建议做**：2.5 结局硬条件（exec/04 已实测推翻）。

## 附：这份清单的维护规矩

- 新增任何"在 prompt 里请模型配合"的改动，**必须**在这里加一行，写清触发条件
  是代码判还是 LLM 判。
- 某条被硬化之后，从第一/二类挪进第三类对照表，不要直接删——"它曾经是软的"
  这个事实对后来人有价值。
- 汇报时不要把这一类改进说成"已修复"，说"已改善（概率性）"。
