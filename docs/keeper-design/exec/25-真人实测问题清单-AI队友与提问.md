## 59 · 「我能不能做 X」被当成行动推进了世界

玩家问「我们能直接去他的地下室吗？」——他要的是一个**答案**（能不能、什么代价）。
守秘人的回应是一整段剧情推进：NPC 进屋、地下室亮灯、传出声响。

### 诊断：分类器缺一格，不是执行层坏了

**执行层早就做对了。** `exec/19 #40` 修过一模一样的症状（问「科比特先生在家吗」
被演成角色在门厅喊话），修法是 `agent.py` 里的 `kp_question` 分支：命中
`question_to_kp` 时**代码强制**收走 `checks` / `san_checks` / `moves` /
`current_node_id`，只留「回答」这一件事。

问题在分类没命中。真实 API 探针，同一局面块换六种发言：

| 玩家说 | `player_state` | 世界被推进了吗 |
|---|---|---|
| **我们能直接去他的地下室吗？** | **`clear_action`** | ✅ 节点挪走 |
| **我可以现在过去敲他的门吗？** | **`clear_action`** | ✅ 节点挪走 |
| 科比特先生是谁来着？ | `question_to_kp` | ❌ |
| 阿铁的侦察技能是多少？ | `question_to_kp` | ❌ |
| 我走到街对面，趴在地下室的窗户上往里看 | `clear_action` | ✅ 挪走 + `spot-hidden` |
| 我们要不要先报警？ | `normal` | ❌ |

🔴 **决定性证据是裁决器自己的 `thinking`**：

> 玩家意图直接闯入科比特地下室，**需判断可行性并推进行动**。

它知道玩家在问可行性，但六个格子里没有这一类,于是选了「推进行动」。
`question_to_kp` 的 prompt 定义把范围限死在「他角色本该知道、但他这个玩家
忘了的设定——他要的是**回忆**」,而「我能不能」不是回忆。

### 为什么是「加一格」而不是「拓宽 `question_to_kp`」

第一版结论是拓宽,理由是「行为完全相同,新加一格等于写一条重复分支」。**推翻了**：
那是实现层的顾虑,而它压倒了更重要的东西。

> 🔴 **枚举的格子是给模型分类用的,不是给代码分支用的。两格行为相同不是问题,
> 定义能不能写干净才是目的。**

硬把「征询许可」塞进「回忆设定」,这个类别就变成「要么…要么…」——**定义含混
本身就是分类错的来源**。同族判据见 `exec/17`：让模型从清晰的白名单里选,不要
让它猜一个含混类别的边界。

执行层照旧复用,`== "question_to_kp"` 改成 `in (...)`,一行。

### 评估过并否掉的更「优」解

| 方案 | 否掉的理由 |
|---|---|
| **把分类拆成独立的一次 LLM 调用** | 理论最干净——现在分类和裁决在同一次调用里,模型「正在写一个推进世界的决定」这件事会污染分类（`thinking` 那句是实据）。但代价是每轮多一次往返,正撞否掉 P6 的那个延迟理由;而且独立调用**照样会分错**,只是少一个污染源。花一次往返买一个概率改善,不划算 |
| 中文疑问句正则前置（"能不能/可不可以/…吗"） | 「我看**能不能**撬开这把锁」是行动。句法特征 ≠ 语义意图,且违反已有教训「中文口语检测正则不能要求关键词紧邻」 |
| 加 `world_advances: bool` 让模型显式表态 | 多一个字段,模型照样可以填 true。没把任何东西变确定 |

### 定性（登记 `exec/20`）

分类这一层**仍是概率性的**。但它下游接的是**代码强制**,所以一旦分对,后果确定。
这是分层的正确形态：**概率的那层尽量做窄,确定的那层兜住**。

唯一的真硬化路径不在我们手里：换成支持 **structured output** 的模型,`enum` 才能
约束到生成侧。DeepSeek 走 JSON mode,`enum` 约束不到（`exec/20` 已记）。

## 60 · AI 队友的权限过大

玩家的原话反馈：「NPC 的话语直接冒出来就很怪」「应该以玩家为主导,NPC 只是
辅助玩家的决策或行动」。

### 诊断：它在结构上是 DMPC,不是 sidekick

事件表时序（同一轮）：

```
11:02:07  就离开(真人)  「我们能直接去他的地下室吗？」        ← 提问
11:02:10  阿铁(AI)      「先别急,我们看看他进屋后有什么动静。」 ← 行动宣言
11:02:16  keeper.state / keeper.node 更新
11:02:23  narration.push
```

**AI 队友把玩家的提问变成了一次行动。** 裁决器这一轮收到两条等权发言,其中
一条是明确的行动宣言,于是按行动裁决。

根子在一条当初写死的原则：

> AI 产出的那句话走跟真人**完全相同**的 `action.submit` 路径,没有任何特权字段。

写它是为了防作弊（读剧本、跳检定）。但——

> 🔴 **「没有特权」和「完全平等」是两件事。它没拿到不该有的特权,却拿到了
> 它不该有的那一半平等：推进世界的权力。**

### 调研：这个形态几乎没有先例,但传统桌游有成熟答案

竞品扫描（完整过程见 Obsidian `调研/`）：COC 那一批全是 GPTs 套壳、单人、
AI 当 KP;Friends & Fables / MacerAI 等通用产品是 AI 当 GM + 真人多人。
**所有产品的 AI 都坐在 KP 那把椅子上,没有一个做「AI 坐玩家席」。**

唯一的直接先例是一个独立开发者 2025-08 的实验（3 个 AI party member + 真人 DM）,
他撞的墙一模一样——模型会「假装成其他角色,甚至假装成 DM」。而他的全部解法是
prompt 约束（1–3 句、每轮一个动作、第一人称、禁旁白）。**唯一的先例用的正是
我们已在用、且已实测失效的手段**,反过来印证 `exec/20` 那句判词：「不主导」
本质上是文风问题,靠措辞硬不了。

传统桌游的答案（D&D 5e, Tasha's）：

| 概念 | 内容 |
|---|---|
| **DMPC** | 公认反模式。归因是**结构性**的：DM 既控制世界又控制一个角色,每一分打在它身上的聚光灯都是从玩家那里拿走的 |
| **Sidekick**（官方替代品） | 定位原文：*intended to fill in for players… to make up for missing capabilities* |
| Sidekick 设计 1 | **升级收益比 PC 少**,原话：*which was done in part to allow NPCs to join adventuring parties **without overshadowing players*** |
| Sidekick 设计 2 | **控制权推荐归玩家,不归 DM**——正是为了躲开 DMPC 陷阱 |
| Sidekick 设计 3 | 数量上限：每个 PC 最多一个 |

🔴 **三条全在机制层,没有一条是行为规范。不是「请你别抢戏」,是「让你在规则上
就够不着」。**

对照下来,阿铁同时踩了三个坑：机制完全对称、控制权归系统（与 KP 同一后端）、
每轮无条件发言。

### 定稿方案：挪进讨论区 + 玩家可指挥

**(a) AI 队友的发言只进讨论区,不进主持人频道。**

查证过它是**结构性**的、不是降低权重：`HISTORY_EVENT_TYPES` 只有
`action.submit` / `narration.push` / `keeper.check|san|hp`,而 `ChatMessage`
在整个 `app/core/keeper/` 里**一次都没出现**——讨论区的内容根本不进裁决器的
任何上下文。

> 与项目一贯判据同构：保密靠「拿不到」不是「请你别说」;这里是**行动权**靠
> 「够不着」,不是「请你别行动」。

**(b) 玩家可以指挥它。** 「我和阿铁一起去地下室探索」是合法的——这在裁决器
眼里是**玩家的**一次行动,阿铁是这次行动的参数,不是发起者。

这两条合起来,把 AI 从「自主体」降成「玩家行动的一部分」,正是 Sidekick 的
控制权设计：**行动权只有真人有,AI 的行动权是派生的。** 而它保住了 AI 队友的
全部实用价值（补位、多一双手、多一套技能）,只切掉「自己决定做什么」。

### 动手前要想清楚的五点

| # | 点 |
|---|---|
| 1 | **`AiPlayerIntent` 的语义要跟着变**：从「我这轮想做什么」（行动宣言）改成「我的看法/建议/疑问」。不只是改措辞,`utterance` 的语义变了。顺带好处：那个开发者的 AI 会假装成 DM 正是因为被要求「行动」,改成「出主意」后输出空间天然收窄 |
| 2 | **「我和阿铁一起去」要能落到 `moves`**：需确认 AI 玩家作为 subject 可寻址。**这是本方案唯一的新代码面**（位置这件事的教训见 `exec/19 #37`） |
| 3 | **阿铁还掷不掷骰**：「让阿铁去撬锁」是辅助玩家的行动,该掷。`_auto_roll_ai_checks` 已存在,保留即可 |
| 4 | **讨论区里要不要每轮都说**：讨论区噪音代价比主持人频道小得多,但每轮插一句仍然吵。最后再看疼不疼 |
| 5 | **玩家指挥它做不合理的事**：Sidekick 规则里 DM 保留否决权。边界情况,先不管 |

### 🔴 60 修好不代表 59 修好

探针里单独提交「我们能直接去他的地下室吗？」（**没有阿铁参与**）照样被分成
`clear_action` 并挪了节点。两条是独立根因,分开修。

## 61 · 裁决的分类与理由不落事件表

诊断 59 时,我拿不到那一轮 `player_state` 的实际值——只能靠复现探针**推断**。

落表的有 `keeper.state`（状态更新）、`keeper.node`（场景指针）、`narration.push`
（叙事）、`keeper.check|san|hp`（结算）。**唯独裁决本身没有**：`player_state`
分类、`thinking`、`narration_guidance` 全部只在日志里,而日志是开发机 stdout,
用户跑的那一局早就没了。

`player_state` 恰恰是「叙事为什么这么写」的唯一解释——59 的根因就藏在它里面。
落表之后这类诊断成本会低一个量级。

> 呼应 `exec/19 #43` 的教训：这类 bug **读叙事永远发现不了,只能读事件表**。
> 那么事件表里就得真的有它。

## 落地记录（2026-08-01，按 61 → 59 → 60 的顺序）

先做 61 是有意的：它做完之后，59 和 60 的效果**当场能从事件表验证**，而不是
再写一次探针去推断。

### 61 落地：`keeper.decision` 事件 + replay 排除

写在**所有代码强制改写之后、执行之前**——那时 `decision` 是最终形态，而
`player_state` / `thinking` 仍是模型的原始输出（`model_copy` 只 update 指定
字段），一条事件同时回答"模型怎么判的"和"代码改了什么"。

🔴 **动手时发现一个必须先解决的前提**：`get_replay` 是**无差别**返回全部
事件、且 `payload` 原样透出的。裁决审计一旦落表就会直接进玩家的复盘——
`thinking` 在 prompt 里明写"玩家看不到"，`player_state` 会暴露守秘人对这句话
的判断。两道防线一起上：

1. `_REPLAY_HIDDEN_EVENT_TYPES` 把 `keeper.decision` 挡在复盘之外；
2. **`narration_guidance` 的内容根本不写进 payload**，只写"哪几条代码强制
   命中了"（`forced` 列表）。guidance 里有"须保密什么"，不写进去就永远不会
   从这条路漏出去——纵深防御，同「保密靠拿不到，不是请你别说」。

排除用的是黑名单而不是白名单：改白名单要动现有全部事件类型，风险不成比例。
**代价写在注释里了——以后新增任何带敏感 payload 的事件类型，必须回来加进那个
集合。**

### 59 落地：`feasibility_question`

`decision.py` 加一格 enum，`prompts.py` 写清它与 `clear_action` 的唯一区别
（**宣告了要做，还是在问能不能做**），`agent.py` 里两类共用"收走推进手段"。

🔴 **实施时发现原方案漏了一半**：原以为可以整条复用 `question_to_kp`，但
`inject_kp_question_guidance` 那段文案通篇在教叙事器"把他角色应该记得的部分
告诉他、用「你记得」起头"——**那是为回忆写的**。玩家问「能不能去地下室」时
套那段，叙事器会去翻他的记忆，而不是回答"能不能、代价是什么"。

所以最终形态是：**收走推进手段共用，guidance 分开**。新增
`inject_feasibility_question_guidance`，内容是"回答能不能/代价/条件，然后把
选择权交回给他"，并明确禁止现编新阻碍或新通路。

测试特意拆成两条：一条验推进手段被收走，一条验 guidance 没串味——只写前者的话，
把 `inject` 改回永远用回忆那段，测试照样绿。

### 60 落地：AI 队友挪进讨论区

`_join_ai_players` 从 `_ingest_utterance`（`action.submit` 通道）改成
`_post_ai_suggestion`（`chat.message` 通道）。`ai_actor.py` 的 prompt 与
`build_view` 的收尾问句一起改了语义：从「你这一轮想做什么」变成「你想对同伴
说点什么吗」，并明确写上"你不能自己行动，真人可以带上你"。

🔴 **「玩家可指挥」这一半不需要新代码，但需要改描述。** 上一轮判断"AI 玩家
在 `moves` 里可寻址是唯一的新代码面"是**错的**——`_resolve_character` 按
`Player.room_id` 查全部玩家、不过滤 `is_ai`，本来就能寻址。真正挡路的是
**语义描述**：`PlayerMove` 的 docstring 和 prompt 里都只写了「谁**没跟着大家**、
单独在哪」，裁决器不会想到用它表达"真人带上了一个没发言的 AI"。

> **能表达但描述挡住了**——跟「schema 表达不了的东西会从叙事里漏出去」是一族，
> 只是这次缺的不是字段，是字段的说明。

时机保持不变（收集窗口关闭后、drain 之前），它仍然是对真人刚说的那句话做反应。
"改成叙事之后再出主意"是另一个决策，等实测觉得别扭再说。

### 磁带

改了裁决 prompt → `test_replay_request_digests_match_recording` 变红，**这是
预期内**（那条测试的 docstring 就写着"变红不代表出 bug，代表 prompt 变了"）。
已用原创迷你剧本重录 `tests/tapes/keeper_minimal.json`。

### 验证

后端 679 passed（新增 6）+ ruff/format/ty，SDK 13 + lint + build，前端
build + lint，e2e 26 passed。

### 改动后的真实 API 探针（9/9）

| 发言 | 分类 | 结果 |
|---|---|---|
| 我们能直接去他的地下室吗？ | `feasibility_question` | 节点停在原地、checks 空 |
| 我可以现在过去敲他的门吗？ | `feasibility_question` | 同上 |
| 要不要先报警？ | `feasibility_question` | 同上 |
| 我需要先做什么准备吗？ | `feasibility_question` | 同上 |
| 科比特先生是谁来着？ | `question_to_kp` | 对照组，没被新格子抢走 |
| 我走到街对面，趴在窗户上往里看 | `clear_action` | 对照组，真行动没被误判成提问 |
| 我现在该做什么？ | `confused` | 对照组 |
| **我和阿铁一起去地下室看看。** | `clear_action` | **`moves` 两个人都挪了** |
| **阿铁，你去敲门，我在这边看着。** | `clear_action` | **只挪阿铁，真人留在原地** |

模型自陈：「玩家在征询可行性，不是宣告行动。回答他，不推进世界。」

最后两条是 #60 里唯一只靠 prompt 描述撑着的部分（`moves` 的第二个用途），
**实测生效，而且比 prompt 里给的例子更细**——真人说了「我在这边看着」，
模型没把他一起带走。

⚠️ 9 个样本、跑了一次。分类这层仍是**概率的**，探针证明的是"新定义能被理解"，
不是"永远分对"。兜底仍然是下游那条代码强制。

## P1 顺带做掉的两条（2026-08-01）

清单里排在 61/59/60 后面的两条产品侧缺口，都是 #55（一键生成写背景）带出来的。

### #4 建卡等待没有文案

一键生成同步等 **7–9.5 秒**（背景那次 LLM 调用），而按钮上只有"生成中…"三个字
——新人会以为卡住了。加了一行等待文案说清在等什么，顺带让他知道这条路的产出
里有背景故事（静态说明也补了半句）。

**没有改成异步**：那会让玩家先看到一张没有过去的卡、然后它突然变出来，比多等
几秒更奇怪。

### #5 背景「换一段过去」按钮

`exec/20 §1.9` 定的方向：**内容质量不该由代码判，该给玩家一个重摇的按钮，让人
来判**。新增 `POST /rooms/{id}/characters/{id}/regenerate-background`，只换过去，
属性/技能/职业一个都不动。

🔴 **失败处理跟一键生成故意相反**：那里写不出来就保持空、卡照常成立（玩家在等
的是卡，背景是锦上添花）；这里玩家**主动点了**，静默保持原样会让他以为按钮坏了
然后一直点 → 显式 503。测试特意断言"失败时原背景没被清掉"——失败不能顺手把他
已有的东西弄没。

🔴 **二次点击确认**：走向导手写过背景的人点下去会被覆盖，而移动端弹 confirm
