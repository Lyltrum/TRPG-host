# 24：长战役 —— 架构评估与扩充方向

> 2026-08-01。起因是用户问「以后要是接长模组怎么办」，并明确要求：
> **不要在已有层面上修修补补，先判断架构够不够支撑，不够就扩充。**
>
> 本文是评估结论 + 方向定稿。**一行代码未动**——落到实现要另开执行规格。

## 结论先行

现在的架构靠三条假设立着，长战役会破掉其中两条，而**真正的架构断裂只有一条**：
世界状态里有一半是模型现编的自由文本，**散文不可裁剪**。

方向不是新架构，是**把 exec/14 已经定下的 `view(subject)` 从可见性贯彻到世界模型**。

---

## 一、战役与短模组是形态差异，不是量级差异

| | 现有短模组（实测五个） | 战役级 |
|---|---|---|
| 节点 | 9–31 | 数百，**分章节/地理区** |
| NPC | 2–10 | 上百，**跨章复现** |
| 事实 | 25–64 | 数百，**第 1 章的线索第 5 章才用** |
| 时长 | 2–3 小时一次跑完 | 几十小时，**跨几十次 session、跨进程重启** |
| 剧本全文 | **7,261 – 21,023 字**（实测） | 十万字量级 |

## 二、三条承重假设

| 假设 | 短模组 | 战役 | 性质 |
|---|---|---|---|
| **A1 整个世界能塞进一次 prompt** | ✅ 21k 字 / 实测整轮 11,134 token | ❌ 超 64K 上下文两倍以上 | 需要结构性改动 |
| **A2 一局 = 一个连续进程** | ✅ | ❌ 必然跨重启 | **工程量，不是架构问题** |
| **A3 世界状态是可整体读写的小 dict** | ✅ 实测最大 561 字节 | ❌ 无法裁剪 | **🔴 真正的架构断裂** |

## 三、A3：为什么它是架构问题而不是容量问题

一份**真实**的 `keeper_state`（本机 2026-08-01）：

```
对局阶段:     investigation          ← 代码写的，枚举
当前场景节点:  initial-scene          ← 代码写的，白名单 id
玩家位置:     <uuid>@initial-scene   ← 代码写的，id@id
已触发议程:    current-situation      ← 代码写的，白名单 id
科比特态度:    警觉、恐惧              ← 🔴 模型现编的键，自由文本
包裹状态:     已被凌铭辉煎烤，部分损毁   ← 🔴 同上
游戏内时间:    第2天 下午              ← 🔴 同上
```

上半截是结构化的，下半截是模型现编的。三个后果：

1. **散文不可裁剪。** 分层注入的前提是"能判断这条该不该给这一轮"。
   `当前场景节点: initial-scene` 判断得了（有 id、有位置）；`包裹状态: 已被煎烤`
   判断不了——它不属于任何地点、NPC、章节。**只要世界状态里还有自由文本，
   分层注入就有一块永远裁不掉的残留，而它恰恰随对局时长线性增长。**

2. **键名是自由文本标识符。** 这一轮「科比特态度」，下一轮可能「科比特先生态度」
   ——两条并存、互相矛盾、谁都不报错。**同一个坑已经踩过三次**：技能名
   （exec/17）、职业名（exec/22），这次踩在世界状态上。

3. **它没有主体。** 「科比特态度」是谁看到的态度？玩家 A 惹恼了他，不在场的
   玩家 B 该不该知道？现在无法回答——而 exec/14 P5.2d 已经为**历史与线索**
   回答过同一个问题（`view(audience) → facts`），世界状态被落在了外面。

## 四、方向：不是新架构，是贯彻已定的抽象

exec/14 终局形态原文：**可见性从「挂在事实上的标签」翻成「挂在主体上的视图」
`view(subject) → facts`**；并写明「**秘密必须有 id；没有 id 的东西就只能是颜色**」。

那条判据当时只对**事实 / 历史 / 投递**兑现了（P0–P5.3）。**世界状态与剧本内容
没有兑现**：它们仍是「一份静态 JSON 全量注入 + 一个散装 dict」。

长战役需要的就是把同一句话贯彻到世界层：

> **世界不是一份剧本加一个笔记本，而是一组有 id 的实体 + 挂在它们身上的状态。
> 上下文是对这组实体的一次查询，不是全量倾倒。**

### 数据模型

模组里的 `nodes / npcs / facts` **本来就是带 id 的实体**，只是现在是只读静态
数据，运行时状态被丢进另一个散装 dict。合并：

```
entity(id, kind, chapter, 静态定义)          ← 来自模组，只读
entity_state(room_id, entity_id, 键, 值)     ← 运行时，代码写，落库
```

「科比特态度：警觉」→ `entity_state(npc:corbitt, attitude, 警觉)`：
**有主体、有位置、有章节 → 可裁剪、可查询、可按受众投递。**

### 上下文分三层（全部由代码算，不由模型决定）

| 层 | 内容 | 何时变 | 估算 |
|---|---|---|---|
| L0 常驻 | 一句话核心真相 · **全局实体索引**（每个实体只给 id+名字+一行身份）· 章节目录与各章状态 · 全局时限议程 · 失败条件 | 整局不变 | ~3k 字 |
| L1 当章 | 本章真相片段、核心线索路径、本章议程；本章节点**只给标题+一行摘要** | 换章 | ~3k 字 |
| L2 当前位置 | 当前节点**全文** + 空间邻接一跳 + 在场 NPC 全文（含数据卡） | 每轮 | ~2k 字 |

空间邻接**数据已经有了**（模组里就有 `邻接（空间）`），位置一直是代码算的
（`current_node_id` + 每人位置）。所以三层全可确定性算出。

### 跨章引用：`needs_entities`

场景：玩家在第 4 章说「我拿第 2 章拿到的那封信去质问第 1 章认识的那个人」。
两章内容都不在注入集里 → 模型会否认信存在、或把人现编。这正是 v1 的病。

**解法：裁决阶段多输出一个 `needs_entities: [entity_id]`（白名单 enum），
代码在叙事阶段之前查表注入详情。**

为什么这不是 tool loop 复活：

- 它是 schema 里的**一个固定字段**，不是自由调用循环；
- 参数是 **enum 不是模型写的字符串**（exec/17 判据：*tool calling 不解决这个，
  enum 才解决*）；
- **零额外延迟**——裁决与叙事本来就是两次调用，中间插的是一次代码查库；
- 兜底是结构性的：即使裁决器没要到，L0 索引里仍有名字与一行身份，
  模型**不会否认存在、也不会编错名字**，最坏只是细节不足。

这条是 exec/19 那条判据的反向应用——*schema 表达不了的东西会从叙事里漏出去*，
那就给它一个口子。

### 记忆三层的配套

- **L1 账本**：已经 id 化，天然可**按章折叠**（往期压成一行，当前章展开）；
- **L2 摘要**：现在每 12 轮一段、每段 120 字；500 轮的战役会攒到 ~40 段 5k 字
  → 需要「章结束时把本章摘要压成一段章摘要」；
- **L3 200 条窗口**：**不用改**。它本来就设计成会丢，重要的在 L1/L2/实体状态。

## 五、🔴 边界：什么**不**实体化

CLAUDE.md 已警告「**全量实体化会压死守秘人的即兴空间**」。死线：

- **剧本里写明的** → 实体，有 id；
- **KP 即兴产生的**（一句氛围、一个路人）→ 留在叙事里，不进状态；
- **中间态**：即兴产物被玩家反复引用时由代码"提升"成实体（可以后做）。

「包裹状态」这类当前落在自由文本里的，多数属于第一类——它就是模组里的物件，
只是 schema 现在没有 `item` 这个 kind。

## 六、什么保持不变（防止读成"推翻重来"）

- **两阶段回合制**（裁决/执行/叙事）不动——已验证，v1 自由 tool loop 的教训还在；
- **两段式玩家掷骰**不动；
- **L1 账本 / L3 窗口**不动；
- **规则权威在后端、掷骰读库**不动；
- **per-audience 上下文裁剪**不动——新的实体视图与它**同构**，是同一套东西向下延伸。

## 七、前置依赖

`ScenarioModule.nodes` 现在是**扁平列表，没有章节层级**。分层注入的第一步是
**模组 schema v4：章节分组 + 章内/跨章标注 + `item` kind**。这也意味着预处理要
能从原文切章——恰好是项目认定的**真正的 agent 命题**（有 `validate_module.py`
当验证器），但还没做过。

## 八、判断：现在该不该做

**长战役不是当前产品目标**（MVP 锚定短模组线索调查）。整套实体化是大投资，
且前置依赖预处理切章。**建议不急着实现整套。**

但有两件事**无论做不做战役都该做**，因为对短模组同样有价值：

### 8.1 `pending` 落库（真 bug，不是战役专属）

`PendingCheckManager` 是**进程内存单例**（其注释自称"实验期妥协"）。后端一重启
队列清空，而 `narrate` 有 pending 守卫 → 会一直回「请先完成待掷的检定」，
**整局死锁**。短模组一次跑完暴露不出来，但它跟战役无关，就是个 bug。

### 8.2 世界状态自由键收口（实体化的第一块砖）

即使不做战役，模型现编键名已经在制造同义键。**过渡形态**：仍允许自由键，
但要求挂在一个已知实体 id 上（`corbitt.态度` 而非 `科比特态度`）。改动很小，
立刻解决"同一件事两个键"，且方向与整套实体化一致——不是白做的过渡层。
