### #1 问"我该做什么"时,KP 复述了之前的剧情而不是给建议

- **模组**:科比特先生
- **症状**:玩家明确问"我该做什么",KP 回复的是重复的前情文字,而不是干脆的建议。
- **诊断**:裁决 LLM 调用**返回了空内容**(重试 3 次仍空),触发兜底决策
  (`agent.py:524` `keeper_adjudicate_fallback`)。"迷茫检测→强制注入引导"这条
  逻辑本身是代码层(`is_player_confused` + `inject_confusion_guidance`),不靠模型
  自觉,正常路径下工作正常(批量质检日志里见过它给出具体方向的案例)。但兜底文案
  (`_FALLBACK_ADJUDICATE_GUIDANCE`:"别编造新剧情,能推进就写行动结果,有障碍就写
  眼前障碍")和迷茫引导("给 1-2 个具体方向")拼在一起时,叙事模型大概率把两者
  揉成了"最安全的选择"——复述已知信息,而不是主动给方向。
- **待确认**:这次裁决为什么返回空(是否与"我该做什么"这类元问题特别容易让
  `deepseek-v4-pro` 的 JSON mode 卡壳有关,还是偶发)。**待复现验证**——需要看
  后续同类提问是否复现同样的空响应。
- **候选修法**(不在本轮改,等问题攒齐一起改):迷茫且裁决走兜底时,不要把
  "别编造/让你重说一遍"这类保守措辞和"给具体方向"的强指令拼在一起——两者语义
  冲突,应该让迷茫引导独占,不掺兜底的保守用语。
- **状态**:✅ 已改(与 #2 同一根因,一并修)——迷茫且裁决走兜底时,不再拼接
  兜底的"别编造/让你重说一遍"文案,直接丢弃只用迷茫引导(`agent.py` 新增
  `is_adjudicate_fallback` 判断)。

### #2 回复文字被硬截断(不是优雅裁切,是话说到一半断掉)

- **模组**:科比特先生
- **症状**:玩家说"行吧,那我想去和科比特先生聊一聊",KP 回复的文字被截断了。
- **诊断**:数据库里这条 `narration.push` 原文只有 **51 字**,结尾停在
  "科比特先生侧身探出，额上"——硬生生断在词中间,没有句号也没有省略号。
  代码里的优雅裁切逻辑(`clip_narration`,句末优先截断 + 补省略号,`max_chars=180`)
  **没有触发**(`keeper_narration_clipped` 日志缺失,因为 51 < 180,判断为"没超长")。
  真正的截断发生在更早一步:`_narrate_prose` 传给 DeepSeek 的
  `max_tokens=280`(`TOKENS_NORMAL`)在模型生成过程中把请求砍断了
  (`agent.py:559`)。
- **🔴 反常之处**:280 tokens 对中文来说正常应该够写出接近 180 字,但实际只写出
  51 字就被砍——token 预算被别的东西吃掉了大半。**最可能的原因**:
  `deepseek-v4-pro`(近期从 `deepseek-chat` 换过来的模型,见 07-28 记忆核实记录)
  本身带推理/思考能力,若默认开启内部推理,那部分 token 也会算进
  `max_tokens` 总预算——模型把预算大头花在"思考"上,只剩一点点用来写可见正文,
  写到一半预算就耗尽了。**这是假设,需要验证**(比如查 DeepSeek 文档确认
  `deepseek-v4-pro` 默认是否带隐藏推理、`usage.reasoning_tokens` 字段能否在
  responses 里读到)。
- **候选修法**(不在本轮改):①如果确认是推理 token 吃预算,要么显式关闭该模型的
  推理模式,要么把 `max_tokens` 预算算法改成"正文预算 + 推理预算"分开计;
  ②给 `_narrate_prose` 补 `finish_reason` 日志,以后一眼能看出是不是被
  `length` 砍断的,不用每次翻数据库。
- **状态**:✅ 已改——实测确认根因(直接调用 DeepSeek API 探针:同样的
  system/user prompt,`usage.completion_tokens_details.reasoning_tokens=77`,
  证实 `deepseek-v4-pro` 默认开隐藏推理且吃 `max_tokens` 预算;加
  `extra_body={"thinking":{"type":"disabled"}}` 后 `reasoning_tokens` 归零、
  正文完整生成)。裁决(`_adjudicate`)和叙事(`_narrate_prose`)两处调用都加了
  这个参数,`narrator.py` 的非 keeper 简单叙事器(`DeepSeekNarrator`)同样加了
  (省 token/延迟)。叙事阶段另外补了 `finish_reason=="length"` 的日志
  (`keeper_narration_hit_token_limit`),以后再被 `max_tokens` 硬砍能一眼看出,
  不用翻数据库。


### #3 叙事正文里直接写出"该掷侦察了"——机制播报泄露进了叙事(新的一类问题)

- **模组**:科比特先生
- **症状**:玩家问"我可以过一下侦查技能吗",KP 描写完场景后,正文末尾直接写
  "该掷侦察了。"——这句话和下方独立的检定卡片("守秘人请求你进行侦察检定")
  说的是同一件事,说了两遍,而且是用機制播报的口吻,不是叙事口吻。
- **诊断**:不是缺规则,是模型没照着已有规则做。发起检定时注入给叙事阶段的
  引导原文是:"由**情境示意**玩家掷骰;绝不编造检定结果,也不要提前描写任何
  要靠这次检定才能获得的信息"(`agent.py:365`)——"示意"要求的是氛围/张力
  暗示,不是直说"该掷 XX 了"这种赤裸的机制播报。查过 `scrub_kp_anti_patterns`
  (正文净化函数),**目前只覆盖两类**:选项菜单(对应质检报告的 `menu_options`)
  和"你可以/如果你"式虚拟挡(对应 `virtual_block`)——**没有任何模式针对
  "机制播报泄露进叙事正文"这第三类失败**,是质检报告四类问题(`too_long`/
  `virtual_block`/`menu_options`/`empty_reply`)之外的新类别,此前没被发现过。
- **候选修法**(不在本轮改):①在 `scrub_kp_anti_patterns` 里补一类模式,识别
  并砍掉"该掷/请掷/进行……检定/该……检定了"这类机制播报句(检定卡片本身已经
  承担"提示玩家该掷骰"这个功能,叙事正文不需要再说一遍);②同时检查这类模式
  会不会误伤正常叙事里合理出现"检定"字样的句子(如 NPC 台词提到"警察会来做
  笔录调查"这种,需要精确到"该/请 + 掷/过 + 技能名 + 检定/了"这种结构,不能
  粗暴按"检定"关键词整句砍)。
- **状态**:待改

### #4 角色卡上的 HP/SAN 数值不随检定结果更新(前端消费缺口,不是 agent 缺口)

- **模组**:科比特先生
- **用户提问**:掷骰判断成功/失败后,HP 和 SAN 值没有实际减少——是不是要设计一个
  单独的工具调用/skill 来执行?
- **诊断**:不需要新工具。查数据库确认这局真实发生过两次变化且都正确落库
  (`keeper.san`:55→54→…→49;`keeper.hp`:10→8,原因"汽车驾驶大失败导致车祸")
  ——后端计算/持久化(`adjust_hp_impl`/`san_check_detail`,`tools.py`)本身没问题。
  缺口在前端有没有把这些数据用起来,而且 HP 和 SAN 是**两种不同性质**的缺口:
  - **SAN(数据有,前端没读)**:`san.check.result` 广播的 payload 里后端已经带了
    `sanRemaining` 字段(`app/dto/ws.py` `SanCheckResultPayload.san_remaining`),
    但前端 `RoomPage.tsx` 处理这个事件时只解构了
    `{playerId, rollValue, sanLoss, result, checkRequestId}`,**没有读
    `sanRemaining`**,也没有调用任何函数把新值写回 `useCharacterStore`——角色卡
    绑定的 `character.derived.san` 因此一直是建卡时的快照。纯前端疏漏,数据早就
    在广播里了。
  - **HP(数据根本没广播)**:HP 变化不走"检定→掷骰→广播结果"这条路径,是裁决
    直接判定伤害后立即执行(`execute_side_effects`),落地方式是把
    "🎲 昵称 · HP a → b" 拼进叙事正文当纯文本广播——**没有任何结构化 WS 事件
    携带新 HP 值**。前端角色卡的 HP 从进房间那一刻就是快照,没有任何机制能更新它,
    连"数据在但没读"都算不上,是协议层缺这个事件。
- **候选修法**(不在本轮改):①SAN 部分改前端,`san.check.result` 处理里读
  `sanRemaining` 并写回角色卡 store,工作量很小;②HP 部分需要给
  `adjust_hp_impl` 生效时补一条轻量结构化广播(类似 `san.check.result` 的模式,
  比如 `character.stat_changed{playerId, hp}`),再让前端接住写回 store——这个
  需要动协议(`app/dto/ws.py` 新事件类型)+ 后端广播点(`ws.py`)+ 前端消费,
  比 SAN 那半个大。
- **状态**:待改

### #5 战斗检定卡片没有生成——技能名解析失败,不是渲染问题(比 #3 更严重的一类)

- **模组**:科比特先生
- **症状**:玩家宣告"那我要制服他",KP 叙事描写了扭打过程,末尾写"该掷斗殴了",
  但**没有出现任何检定卡片**,对话直接卡在这里,这场战斗从头到尾没有真正掷过骰。
- **诊断**:裁决本身判断完全正确——`keeper_decision` 日志显示
  `checks=['斗殴']`,thinking 写的是"应发起斗殴检定对抗",语义合理。但
  `create_pending_checks` 调 `_resolve_skill_target` 解析"斗殴"时报错:
  `未知的技能/属性名「斗殴」`(`keeper_pending_check_issues` 警告日志)。
  **根因**:COC7 规则表里这个技能的规范名是复合名 `格斗：斗殴`,不是裸词
  `斗殴`;`_resolve_skill_target`(`tools.py:146`)只做精确匹配
  (`wanted in (spec.id, spec.name)`),只硬编码了一条同义词归一(侦查→侦察),
  **没有处理复合名技能的短名匹配**。裁决器/叙事器说人话用短名("斗殴"/"手枪"/
  "生物学"/"船舶")是完全自然的,没人会说"格斗：斗殴"这种规则书写法。
- **🔴 影响面**:规则表里共 **33 个复合名技能**(格斗系 7 个:斗殴/剑/斧/矛/鞭/
  链枷/刀/链锯;射击系 6 个:手枪/步枪霰弹枪/冲锋枪/机枪/弓/火焰喷射器;科学系
  14 个:药学/生物学/化学/物理学/……;驾驶系 5 个:马车/飞行器/船舶/航天器/
  热气球)。**任何一次涉及这些技能的检定,只要模型说短名就会静默失败**——
  失败被 `issues` 吞掉、喂给叙事阶段"自然圆场"(不暴露技术细节),
  于是玩家看到的是叙事写得煞有介事地喊"该掷 XX 了",但检定机制其实从未存在过。
  **这是之前 07-24 组装阶段"B 验证观察"里已经点过名的缺口**(A 类缺口 #6
  "技能名归一摩擦:自由中文短名 vs COC7 复合名"),当时只是理论推测,这次真人
  实测里第一次撞上真实后果——一场战斗遭遇完全没法用骰子解决。
- **候选修法**(不在本轮改):`_resolve_skill_target` 补一层复合名短名匹配——
  裸词能唯一定位到某个复合技能的子类名时(如"斗殴"只对应`格斗：斗殴`一个)
  直接命中;需要考虑歧义场景(比如"驾驶"裸词本身对应 5 个子类中的哪个,不能
  瞎猜,应该报错或者要求裁决器给出更明确的子类)。
- **状态**:待改
